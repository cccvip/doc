# 一次压测调优复盘：从 6.68% 的拒绝率到「等一条连接」

这次压测一开始只看到一行异常，最后却翻到 Druid 的取连接上。中间我猜错了四次——线程池、CPU、连接抖动、行锁，每次都被数据推翻。

所以这篇不只是记录"改了什么"，更想记录**每一轮当时是怎么想的、拿到什么证据、为什么那个假设不成立**。如果你也在压测里追一个"RPS 上不去但 CPU 也不高"的问题，前面这几轮的弯路你可以直接跳过。

> 全文的数字都来自真实压测和火焰图，没有估算。想直接看结论可以跳到「根因」和「小结」。

# 现场

- 接口：`POST /http/peopleAccounted/v1.0/operateCRStudentToPending`，单个学生状态流转
- 压测工具：Locust，稳态 601 RPS
- 结果：`36148` 次请求，`2416` 次失败（**6.68%**），平均 `884.92ms`，最小 `37ms`，最大 `5963ms`
- 异常：`java.util.concurrent.RejectedExecutionException: operateExecutor full`
- 环境：容器 1.5GB 内存、JVM 堆 896MB、可用 CPU 2~4 核（`ParallelGCThreads=2`）、Tomcat 9.0.75、Redis 7.x

`RejectedExecutionException` 看着像线程池的问题，但**它只是最外层最先崩掉的那一环**。这条链路一共 6~7 次串行往返：

```text
① Redis  SISMEMBER 校验学生是否属于该事件
② MySQL  master INSERT（generateNotificationId 发号）
③ MySQL  icrisisgoRo 两条 SELECT（getGroupBasicInfo）
④ 提交异步任务 operateExecutor → 异步写库
⑤ Redis  lua  写状态 + seq
⑥ Redis  pipeline 读回 markStatus / markComment
⑦ RabbitMQ 发送
```

# 总览：最后的结论

**异步任务里约 60% 的时间花在 `Druid/Connection/getConnection` 上，而根因是「线程池大小」和「连接池大小」相等——零余量。**

```text
operateExecutor  max = 40   ┐
                            ├── 40 个线程抢 40 条连接，余量 = 0
ecommWR  max-active = 40    ┘
        ↓
getConnection 排队 ~25ms（占比 60%）
        ↓
单任务耗时被抬到 40~70ms
        ↓
池产能 = 线程数 / 单任务 = 561/s  <  需求 601/s
        ↓
AbortPolicy → 6.68% RejectedExecutionException
```

链条上每一环都有一个具体的数字支撑，下面逐轮说。

# 第一轮：线程池溢出（症状，不是病）

配置是这样的：

```java
int core = Runtime.getRuntime().availableProcessors();   // 容器里返回 2 或 4
ThreadPoolExecutor pool = new ThreadPoolExecutor(
        core, core * 10, 3, TimeUnit.SECONDS,
        new LinkedBlockingDeque<>(2000),
        threadFactory);                                  // 默认 AbortPolicy
```

这里有个**容易忽略的语义**：`execute()` 是"核心满了先入队，队列满了才扩容到 max，max 也满了才拒绝"。所以队列一旦深到 2000，`max` 基本永远生效不了，**实际并发恒等于 `core`**。

用压测数据反推池子的实际产能：

```text
被接受的任务 = 601.37 − 40.19 = 561.18 /s
按 Little's Law：需要线程数 = 601.37 × (线程数 / 561.18)
```

反推出来的单任务耗时是 36~71ms（取 20 还是 40 个线程取决于 `availableProcessors()` 的真实返回值）。**结论：确实是池子溢出，但此时"把 max 加大"只是把并发推给数据库**，属于权宜之计。

当时做了一件事：把拒绝策略改成抛带名字的异常（`responsibleExecutor full`），让失败可见——这个决定后面帮了大忙，6.68% 这个数就是它吐出来的。

> 另一个同时做的调整是把队列从 2000 降到 200。**这不是性能优化，是让过载变得可见**：队列 2000 会把"拒绝"变成"DB 滞后 3.6 秒更新"，更难查。

# 第二轮：以为是 CPU（被数据推翻）

第一张 CPU 火焰图（16,170 个样本）看起来"到处都是浪费"：

| 帧 | 占比 |
|---|---|
| `LoggerConfig.log` | 16.14% |
| `Log4jLogger.error` | 18.34% |
| `Druid WallFilter.preparedStatement_execute` | 5.79% |
| `ParameterizedOutputVisitorUtils.parameterize` | 2.08% |
| `AbstractLogger.getLocation` / `StackLocator.calcLocation` | 8.87% / 4.50% |
| `InstMethodsInter.intercept`（SkyWalking agent） | 67.37%（inclusive） |

当时判断出两个真问题，都改掉了：

**① `WallFilter` 是默认开着的。** 我们并没有配 `filters`，但 `dynamic-datasource` 3.1.1 的 `DruidDataSourceCreator` 里有这样一段兜底逻辑（从字节码看出来的）：

```text
631: invokevirtual  getFilters()      // 先看单个数据源的 filters
638: getfield       filters:String    // 再看全局 DruidConfig.filters
646: ifnonnull      653
649: ldc            "stat,wall"       // ← 两个都为 null 时，默认 "stat,wall"
```

也就是说：**不配 `filters` 反而全开了**。改成 `filters: stat` 之后，`WallFilter` 从 5.79% 归零，`parameterize` 也归零。

**② log4j2 的 pattern 里有 `%M-%L`。** 只要 pattern 里出现 `%L / %l / %line / %M / %method / %F / %C / %class` 中任意一个，布局就会打开 `includeLocation`，**每一条日志都要 `new Throwable().getStackTrace()`**。而我们的栈深度是 **179 层**，所以一次行号计算要填 179 个 `StackTraceElement`。

改完再压：

| 项目 | 改前 | 改后 |
|---|---|---|
| `WallFilter.preparedStatement_execute` | 937 (5.79%) | **0** |
| `getLocation` | 1435 (8.87%) | 1037 (6.04%) |
| `Log4jLogger.error` | 2965 (18.34%) | 2008 (11.70%) |
| 整个 handler | 6321 (39.09%) | 5989 (34.90%) |

**CPU 确实降了 5~6 个百分点——但 RPS 一点没动。**

这一句是整轮排查的转折点：**CPU 不是瓶颈**。后面所有精力都应该从"省 CPU"挪开。

> 顺带一个教训：`getLocation` 只从 8.87% 降到 6.04%，说明 `%M` 和 `%L` 只去掉了其中一个。**location 只要还剩一个 token 就还是 true**，要把所有 token 都清掉，包括每个 appender 各自的 `<PatternLayout>`。

# 第三轮：转向数据库（一半被推翻）

CPU 排除后，第一反应是看 DB。两个指标直接分出了方向：

```sql
SHOW STATUS LIKE 'Threads_created';    -- 几乎不涨
SHOW STATUS LIKE 'Threads_running';    -- 一路上涨
```

**`Threads_created` 不涨，直接推翻了"连接在反复创建"这个假设。** 火焰图里 `CreateConnectionThread` / `DestroyConnectionThread` 各占 2.1% 也不是抖动——wall 采样对每个存活线程是均匀的，而**每个 Druid 池各有一个建连接线程和一个销毁线程**，9 个池正好是单线程基准（`TimerThread` 9,064 个样本）的 9 倍。**那是"池子数量"的指纹，不是"抖动"的指纹。**

**`Threads_running` 一路上涨**说明另一件事：同一时刻有越来越多查询在 DB 里跑。配合索引（`idx_stu_uuid (record_id, stu_uuid)` 正好匹配 `WHERE record_id=? AND stu_uuid IN (...)`）已经是最优，只剩一个可疑对象——锁。

```sql
Innodb_row_lock_waits    +2000 次
Innodb_row_lock_time_avg 51ms
```

看着很像根因，但算一下账：

```text
累计锁等待 = 2000 × 51ms ≈ 102 秒
摊到 30000 个异步任务 = 每个任务平均 3.4ms
占单任务耗时（40ms）的比例 ≈ 8%
```

**8% 解释不了那 40ms，也解释不了 6.68% 的拒绝。** 锁是二级因素，不是根因。

> 这里顺带确认了锁的来源：`WHERE record_id=? AND stu_uuid IN (...)` 用的是正确的复合索引，不同学生的行在索引里是不同条目，next-key / gap 锁在 RR 下彼此兼容——**只有两个事务更新同一个学生时才会真阻塞**。`Innodb_row_lock_waits` 只涨 6.7%，说明是"偶发重叠"，更像是压测脚本在反复打同一批学生，而不是系统性的锁设计问题。

# 第四轮：wall 火焰图（推翻"要加 Tomcat 线程"）

CPU 图看不到"等待"，所以又抓了一张 **wall clock profile**（3,875,381 个样本）。两个结论：

```text
TaskQueue.poll      1,621,785   41.85%
LoggerConfig.log    1,750,512   45.17%
```

**① `TaskQueue.poll` 41.85%** —— 那是 Tomcat 工作线程**在队列上空转等任务**。`runWorker` 总共 57.22%，其中 41.85% 在 `poll`，也就是 **Tomcat 线程约 73% 的时间是空闲的**。

这一条直接否掉了最开始那个问题：「要不要调 Tomcat 线程数」。答案是**不用，而且方向相反**——瓶颈在 DB，加大 HTTP 线程只会往里灌更多并发。

**② `LoggerConfig.log` 占 45% 墙钟，但 CPU 只有 16%** —— 中间那 29 个百分点全是在等：`RollingFileAppender` 写磁盘、`GRPCLogClientAppender` 用 gRPC 发日志。日志是**同步**的，请求线程只能干等。

> 这条后来改成了异步 appender，但它也不是最终答案——它解释了墙钟的一部分，解释不了"为什么 RPS 不动"。

# 第五轮：SkyWalking 的异步 trace（决定性证据）

前面几轮都是"从外部指标推"，最后一步是**直接看那个异步任务内部**。它被 SkyWalking 的线程池插件包成了 `SwRunnableWrapper`，所以有一条独立的 trace：

| Span | 占任务时长 |
|---|---|
| **`Druid/Connection/getConnection`** | **约 60%** |
| `Mysql/JDBC/PreparedStatement/execute` × 2 | 约 25% |
| `Mysql/JDBC/Connection/commit` | 约 5% |
| `Jedis/sync` × 2 | **< 1%** |

**答案就在这里：那 40ms 里有一大半是在"等一条数据库连接"。** 不是 SQL 慢，不是 Redis 慢，也不是 commit 慢。

回过头看配置，原因难看得有点刺眼：

```text
operateExecutor  max = 40      ← 最多 40 个线程并发
ecommWR  max-active = 40       ← 池里最多 40 条连接
```

**40 个线程要 40 条连接，余量是 0。** 只要有一条连接还没 close、或者某次请求稍微慢一点，线程就开始在 `getConnection` 里排队。而队列一等，单任务就从 8ms 涨到 40ms，池子产能从几千/s 掉到 561/s，于是 6.68% 的请求被拒绝。

这也顺带解释了另外两个一直没想通的现象：

- **DB CPU 只有 60%**：连接都还没拿到，SQL 当然跑不满；
- **`Threads_running` 一路上涨**：连接陆续拿到后，同一 `record_id` 上的事务堆在一起，才有了那 2000 次行锁等待。

# 根因

一句话：**异步线程池的大小等于（甚至超过）它要用的连接池大小，等于把并发压力全部转成"取连接排队"。**

```text
getConnection 排队  ≈ 60% 的任务耗时
        ↓
单任务 40~70ms（而不是理论上 5~10ms）
        ↓
池产能 561/s < 需求 601/s
        ↓
AbortPolicy → 6.68% RejectedExecutionException
```

# 修复

**① 保证「线程数 < 连接数」，并且留出余量**

这是唯一真正的解。两边相等时，池子永远是饱和的。

```java
new ThreadPoolExecutor(
        8, 16,                              // 线程数明显小于连接数
        60, TimeUnit.SECONDS,
        new LinkedBlockingQueue<>(200),
        threadFactory,
        new ThreadPoolExecutor.CallerRunsPolicy());
```

```yaml
spring:
  datasource:
    dynamic:
      druid:
        initial-size: 10
        min-idle: 10            # 注意：min-idle 是「常驻」，6 个池 × 20 = 120 条会被永久占住
        max-active: 40
        max-wait: 3000
        filters: stat           # 默认是 stat,wall，wall 要显式去掉
        test-while-idle: true
        test-on-borrow: false
        keep-alive: true
        keep-alive-between-time-millis: 60000
        min-evictable-idle-time-millis: 600000
      datasource:
        ecommWR:
          druid:
            max-active: 60      # 只有异步写库这个池需要额外余量
```

原则有两条：**池线程数 ≤ 连接池 max-active 的一半**；**Σ(所有池的 max-active) < MySQL max_connections × 0.8**（这一点很容易忘——`max-active` 在 `dynamic.druid` 下是**全局**的，6 个数据源会各配一份）。

**② 拒绝策略换成 `CallerRunsPolicy`**

池子满了就让提交线程自己跑，而不是抛异常。这里调用方是 HTTP 线程、任务是几十毫秒的 DB 写，正好是 `CallerRunsPolicy` 最合适的场景（如果调用方是定时调度线程就别这么用，会拖住调度器）。

效果：**不再报错、不丢数据**，过载时只是这个请求慢一点——这才是反压该有的样子。

**③ 事后回收连接池参数**

为了验证诊断，当时把 `max-active` 一次拉到了 200。验证完必须收回：

- `max-active: 200 → 40~60`：4 核 DB 用 200 条连接，只会增加闩竞争和上下文切换；
- `min-idle: 20 → 10`：`min-idle` 是**常驻**的，配合 `keep-alive` 永远不会回收，6 个池 × 20 = 120 条会一直占着 MySQL 的连接配额。

# 另一条线：一个下载接口的内存崩溃

同一轮压测还顺带查了一个"服务器内存崩溃"的问题，结论和上面完全无关，但同样典型，记一笔。

现象是进程被直接杀掉，而 GC 日志干净得不正常：**0 次 Full GC、GC 后存活只有 180MB（堆上限 896MB）、日志戛然而止**。这排除了"堆被打满"——如果是堆 OOM，G1 一定会先打若干次 Full GC 并留下 heap dump。干净地断掉，说明是**非堆内存**耗尽（或外部 kill）。

真正的问题在 `downloadControlledReleaseRecordBaseInfoFile` 的读流代码：

```java
int byteLength = 1024 * 64;
byte[] bytes = new byte[byteLength];
int read;
ByteBuffer allByteBuffer = ByteBuffer.allocate(0);
while ((read = (is.read(bytes))) != -1) {
    byte[] array = allByteBuffer.array();
    allByteBuffer = ByteBuffer.allocate(allByteBuffer.capacity() + read);   // 每读 64KB 就把全量重分配一遍
    allByteBuffer.put(array);
    allByteBuffer.put(bytes, 0, read);
}
```

每读一个 64KB 块，就**把"目前为止的全部内容"重新分配一遍并拷贝两遍**。设文件大小 S，总分配量约 `S² / 128KB`：

| 文件大小 | 循环次数 | 总分配量 |
|---|---|---|
| 1 MB | 16 | 8 MB |
| **4 MB** | 64 | **134 MB** |
| 10 MB | 160 | **839 MB** |
| 50 MB | 800 | **21 GB** |

改成 `ByteArrayOutputStream`（翻倍扩容、均摊 O(S)）之后，4MB 文件的分配量从 134MB 降到约 8MB。

# 面试怎么讲这个问题

这段是给面试准备的——同一个故事，讲 30 秒和讲 3 分钟，效果完全不一样；而**面试官追问的那几句，才是真正考察的地方**。

## 三十秒版本

> 压测一个状态流转接口时，6.68% 的请求抛 `RejectedExecutionException`，平均延迟 885ms。一开始都以为是线程池太小，但加大线程、优化 CPU 都没用。最后在 SkyWalking 的异步任务 trace 里看到，**60% 的时间花在 `Druid/Connection/getConnection` 上**——异步线程池 40 个线程，连接池也是 40 条，余量为零，线程全在排队等连接。把线程数降到 16、给连接池留出余量之后，单任务从 40ms 掉到 8ms，拒绝归零。

这段话的作用是让面试官抓到一个**反直觉的点**（线程池和连接池比例失调），他大概率会往下追问。

## 三分钟版本

按"现象 → 排查 → 根因 → 修复 → 验证"讲，但**每一轮只讲「假设 + 被什么数据推翻」**，这样听的人能看到你的方法，而不是一堆配置项：

1. **现象**：拒绝异常 + 平均 885ms + 最小 37ms（这个最小值很重要，说明代码路径本身不慢，时间是在等）；
2. **假设一：线程池太小** → 算出池产能 561/s < 需求 601/s，确实溢出了，但加线程只是把并发推给 DB，是权宜；
3. **假设二：CPU 是瓶颈** → 优化掉 5~6 个点的 CPU（关 WallFilter、去掉 log4j2 的 `%L`），**RPS 一点没动** → CPU 排除；
4. **假设三：连接在抖动** → `Threads_created` 不涨 → 排除；
5. **假设四：行锁** → `2000 次 × 51ms` 摊到 3 万个任务只有每个 3.4ms，占 8% → 不是主因；
6. **决定性证据**：SkyWalking 里那条异步任务的 trace，`getConnection` 占 60%；
7. **根因**：`operateExecutor.max = 40`，`ecommWR.max-active = 40`，零余量；
8. **修复与验证**：线程数 40 → 16，连接池留余量，拒绝策略换 `CallerRunsPolicy`；`getConnection` 的时间片收缩，单任务 40ms → 8ms，失败率归零。

## 大概率会被追问的问题

**Q1：`RejectedExecutionException` 是怎么产生的？**

`execute()` 分三段：线程数 < core 就建线程；否则入队；队列满且线程数 < max 才扩容；都满了才走拒绝策略。所以**队列深的时候 `max` 基本失效**——队列没满就轮不到扩容，实际并发恒等于 core。

**Q2：为什么加线程没用？**

因为瓶颈不在池子的线程数，而在任务要用的下游资源。加大线程只是把更多请求同时压到同一个资源上，单任务耗时反而变长，而 `产能 = 线程数 / 单任务耗时`，可能不升反降。判断依据是"CPU 没到顶 + 下游在排队"。

**Q3：CPU 都降了，RPS 为什么不动？**

这本身就是结论：**CPU 不是约束条件**。如果 RPS 是 CPU 限制的，砍掉 6 个百分点应该能看到吞吐变化。所以判断容量要看**延迟-吞吐曲线的拐点**——加压后 RPS 不涨、延迟涨，才是到顶，而不是看 CPU 百分比。

**Q4：CPU 火焰图和 wall 火焰图有什么区别？**

CPU 模式只采样"在 CPU 上跑"的线程，回答**CPU 花在哪**；wall 模式对所有存活线程定时采样，回答**时间花在哪等**。同一份代码，CPU 图里日志占 16%，wall 图里占 45%，中间的 29 个点全是在等磁盘和 gRPC。**所以两张图的百分比不能跨口径比较。**

**Q5：怎么判断数据库是不是到压力上限了？**

看三个东西，都不看 CPU 百分比：`Threads_created` 是否持续上涨（连接有没有反复创建）、`Threads_running` 是否持续上涨（并发是否在堆积）、以及阶梯加压下的延迟-吞吐拐点。CPU 60% 什么都不能说明——可能 60% 全是有效工作，也可能只有 60% 但线程全在等锁。

**Q6：有行锁等待，为什么说不算根因？**

要看量。`Innodb_row_lock_waits` 涨了 2000 次、平均 51ms，累计 102 秒；但摊到 3 万个异步任务上只有每个 3.4ms，占单任务耗时的 8%。**"有锁等待"不等于"锁是瓶颈"**，得用 `次数 × 平均等待` 算出它对总耗时的实际贡献。

**Q7：线程池和连接池该怎么配？**

核心是**比例**：池线程数应当明显小于连接池的 `max-active`，一般留一半余量。两者相等时池子永远饱和，`getConnection` 就变成主要耗时；反过来，线程数降到连接数的一半，单任务可能从 40ms 掉到 8ms，**吞吐反而翻倍**——争用同一个资源时，少并发胜过多并发。

**Q8：`CallerRunsPolicy` 什么时候能用，什么时候不能用？**

能用：调用方是业务线程、任务本身不敏感（比如异步写库），池满时让提交线程自己执行，把"拒绝"变成"反压"。不能用：调用方是定时调度线程或网络 IO 线程——那会把调度/IO 线程一起拖住，造成更严重的抖动。

**Q9：`min-idle` 和 `max-active` 有什么区别？**

`min-idle` 是**常驻**的空闲连接数，池子会主动补到这个数；`max-active` 是上限。配 `min-idle` 时要乘上数据源个数——`dynamic.druid` 下是全局配置，6 个数据源 × 20 = 120 条连接会被 `keep-alive` 永久占住，很容易把 MySQL 的 `max_connections` 吃光。

**Q10：再来一次，你会怎么更快定位？**

先画一张链路图，把每个远程调用点标出来；然后用链路追踪看一次慢请求的**分段耗时**，直接定位到是哪一段；再用 wall 图确认那一段是在算还是在等。这次花了五轮才收敛，原因是**一直在外部指标上推理，没有第一时间去看任务内部的分段**——外部指标只能排除，不能定位。

## 可以主动抛的钩子

讲的过程中可以顺手带两句，把话题引到自己熟悉的地方：

- "顺便一提，Druid 的 `filters` 在 dynamic-datasource 里默认是 `stat,wall`，不配反而全开，WallFilter 会解析每一条 SQL。"
- "log4j2 的 pattern 里只要有 `%L`/`%M`，每条日志都会构造一次 `StackTraceElement` 数组；我们的栈深 179，所以单次行号计算特别贵。"

## 几句不要说的话

- **不要说"我把连接池调到 200 就解决了"。** 那是掩盖不是解决，而且 200 条连接对 4 核的 DB 是有害的。要讲**比例关系**。
- **不要只报配置。** 每改一个参数都要能说出"是什么数据支撑了这个判断"。
- **不要提那些没验证完的猜测**（比如"一开始怀疑是 GC"），除非你能紧跟一句"后来用什么排除了它"。半截的猜测在面试里是减分的。
- **不要把它讲成"调参调好的"**。这个案例真正的价值是**用数据否掉四个错误假设**的过程。

# 小结

这次调优真正值钱的不是那几个配置，而是下面这几条方法论。

1. **`RejectedExecutionException` 是症状，不是病因。** 先顺着它找到"任务为什么慢"，而不是急着调池子参数。

2. **CPU 百分比不是容量指标。** 我们砍掉了 5~6 个百分点的 CPU，RPS 一动不动——这就证明了 CPU 不是约束。判断容量要看**延迟-吞吐曲线的拐点**：加压后 RPS 不涨、延迟涨，才是到顶。

3. **CPU 图和 wall 图必须分开抓，百分比不能跨口径比较。**
   - CPU 图回答"CPU 花在哪"（能不能扛更多 RPS）；
   - wall 图回答"时间花在哪等"（延迟为什么高）。
   - 拿 CPU 图的百分比去解释延迟，一定会误判。

4. **一次只改一个变量。** 这一轮同时改过拒绝策略、队列、CPU 相关配置，导致有两次"改了但不知道是谁起的作用"。

5. **先量，再猜。** 这次猜错了四次（线程池太小、CPU 是瓶颈、连接在抖动、行锁是根因），每一次都是被一个具体的计数器推翻的：
   - `Threads_created` 不涨 → 不是连接抖动；
   - `Innodb_row_lock_waits × avg` 只占 8% → 不是锁；
   - CPU 降了 RPS 没涨 → 不是 CPU。

6. **火焰图有自己的坑。**
   - `--threads` 模式会改变栈展开方式，agent 的帧可能被省略（`InstMethodsInter` 从 68% 掉到 0.25% 是假象），不能用来比较框架开销；
   - CPU 模式下会出现 `clone` 这种"归因失败"的桶，看到 30% 别急着当结论，用 `--threads` 再看一次，或者用 `jstack` 数线程；
   - 采样是瞬时的，单张图不算数，压测稳态里抓 5~10 次看频次。

7. **连接池不是越大越好，关键是和线程数的比例。** 线程数 ≈ 连接数时，池子永远饱和；线程数降到连接数的一半，单任务耗时可能从 40ms 掉到 8ms，**吞吐反而翻倍**。

8. **`min-idle` 是常驻内存。** `dynamic.druid` 下的配置对所有数据源生效，6 个池 × 20 = 120 条连接会被 `keep-alive` 永久占着，配之前先算一遍 MySQL 的 `max_connections`。
