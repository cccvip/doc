并发程序为什么难写？很大程度上是因为**可见性**——一个线程改了共享变量，另一个线程却可能看不到。这篇把 JMM 怎么定义可见性、volatile / synchronized 又是怎么保证可见性的讲清楚。

> 这篇是"可见性"的专题，和 [Synchorized.md](Synchorized.md)（锁与锁升级）、[ReentrantLock.md](ReentrantLock.md)（AQS）互补。

# 总览：为什么会有可见性问题

**可见性（Visibility）** 指：一个线程对共享变量的修改，另一个线程能否（及时地）看到。它是 JMM 要解决的三大问题之一：

- **原子性**：一个或多个操作要么全执行、要么全不执行（`i++` 不是原子的）；
- **可见性**：一个线程的写，其它线程能否读到；
- **有序性**：指令是否按代码顺序执行（编译器 / CPU 会重排序）。

问题有两个根源：

1. **CPU 多级缓存**：每个核心有自己的缓存，写操作先落缓存，别的核心不一定马上看到 → 缓存一致性问题；
2. **指令重排序**：编译器、指令调度器、CPU 为了性能会重排无依赖的指令，单线程语义不变，多线程就可能出错。

# 为什么会重排序（摘抄）

> 以下摘自 [一篇讲内存屏障的文章](https://blog.csdn.net/tjcwt2011/article/details/123652951)，作者从"程序运行环境"这个更底层的视角解释重排序与内存屏障，写得很通透，原文摘录如下。

程序是工作在 OS、编译器、物理硬件共同营造的虚拟环境中的（本文称之为"程序运行环境"）。程序运行环境有一定的规则，不同的 OS / 编译器 / CPU 有千万种方法来实现这个规则，但规则本身是不变的。我们要看到规则，而不是实现——架构眼光就是要从所有实现中看到不变的部分（承诺的规则）和可变的部分（实现的规则）。

先看如下程序序列：

```c
a = 1;
b = 2;
c = a + b;
printf("a=%d, b=%d, c=%d\n", a, b, c);
```

这个程序序列作用于运行环境时，规则**承诺**的是：计算 `c` 时 `a` 必为 1、`b` 必为 2，最后打印 `c` 必为 3。

但它**没有承诺**的是：

1. `a`、`b`、`c` 是内存上的地址（也可以是寄存器一类的东西）；
2. `a` 先变成 1、然后 `b` 才变成 2；
3. 如果其它设备或 CPU 修改这些内存地址，反应是什么；
4. 等等。

所以，编译器和 CPU 在满足"承诺"的前提下，总是玩各种小九九，**（非有意地）破坏没有承诺的规则**。这种破坏不仅出现在 Cache 上，还常出现在：

1. **编译器**：通过重排指令充分利用寄存器和流水线，可能把 `b=2` 排到 `a=1` 前面；
2. **指令调度器**：重排指令执行步骤，甚至改寄存器索引名，引起生效时间改变；
3. **指令发射器**：多 Issue 的 CPU 可同步发出多条无依赖指令，先后顺序受执行影响，不一定和软件输入一致；
4. **Cache 系统**：即使保证指令发射依赖，Cache 到达内存的时间也受多级调度算法影响；
5. 等等。

但程序只有一个，它不能替你去考虑编译器、指令发射的问题——如果每下一步都要想 Cache 上会形成怎样的执行序列、编译器又会怎样编排，程序就没法写了。所以 SMP 系统中 Linux 增加了 `smp_mb()` 系列操作，不同平台实现不同，但都必须遵守新的规则：

- `smp_mb()` 结束后，对**本 CPU** 来说，运行环境保证 `smp_mb()` 之前的内存操作已完成并反映到内存子系统；
- 同时，内存子系统中所有未竟操作，在 `smp_mb()` 后必须对本 CPU 生效。

由此可理解一个经典案例：为什么第一个线程已经用了 `smp_mb()`，第二个线程还需再 `smp_mb()` 一次——因为第一个线程只保证对本 CPU 和内存子系统生效，并不保证对第二个 CPU（它有自己的 Cache 等环境）生效。`mb()` 系列类似，只是面对 CPU 与 IO，而非 CPU 与 CPU。

> 上文的 `smp_mb()` 和 Java 里的内存屏障，本质是同一件事在不同层面的实现。

# JMM 与 happens-before

JMM 用"**主内存 / 工作内存**"抽象：每个线程有自己的工作内存（对应 CPU 缓存 / 寄存器），共享变量存主内存，线程读写在各自工作内存进行。可见性问题的本质，就是工作内存与主内存不同步。

JMM 用 **happens-before（先行发生）** 规则定义可见性：若 A happens-before B，则 A 的结果对 B 可见。主要规则：

| 规则 | 含义 |
|---|---|
| 程序顺序 | 同线程内，前面的操作 hb 后面的操作 |
| 监视器锁 | 对同一锁的解锁 hb 后续的加锁 |
| volatile | volatile 变量的写 hb 后续对它的读 |
| 线程启动 | `Thread.start()` hb 新线程内所有操作 |
| 线程终止 | 线程内所有操作 hb 其它线程检测到它结束 |
| 传递性 | A hb B、B hb C ⇒ A hb C |
| 中断 / 终结 | `interrupt()` hb 检测到中断；构造完成 hb `finalize()` |

> 注意：x happens-before y 不是说 x 一定在 y 之前执行，而是说 **x 的结果对 y 可见**——只要满足可见性，发生了重排序也无所谓。

# 实现可见性的两种手段

笼统地说，实现可见性无非两种：

1. **线程切换**——切换时重新加载上下文与缓存。注意：**LockSupport 本身不保证可见性**，真正起作用的是 park/unpark 背后的 happens-before，以及线程切换时对上下文的重新加载。
2. **内存屏障**——即 volatile 的内存语义。

## 一、线程切换

### 过程

1. **保存当前线程上下文**：程序计数器（PC，指向下一条指令）、CPU 寄存器（通用寄存器、指令指针等，存中间结果和状态）、栈指针等，保存到该线程的内核栈或线程控制块（TCB）；
2. **选择下一个线程**：OS 按调度算法（优先级、等待时间、执行时间等）从就绪队列挑一个；
3. **恢复下一个线程上下文**：从它的内核栈 / TCB 恢复 PC、寄存器等，让 CPU 从上次暂停处继续，好像从未中断。

### 开销

- **时间开销**：保存 / 恢复上下文期间 CPU 无法执行有效任务，频繁切换会累积，降低利用率；
- **空间开销**：保存上下文要占内核栈 / TCB 等空间，线程多时内存吃紧；
- **缓存失效开销**：新线程的数据 / 指令可能不在 CPU 缓存里，需重新从内存加载，增加访问延迟。

**总结**：线程切换时，CPU 会重新加载上下文信息，并把内存数据重新加载到本地缓存。

## 二、内存屏障（volatile 的内存语义）

内存屏障对不懂计算机组成原理的人很抽象，但一句话概括：**通过内存屏障要求计算机执行操作时，如同你所见的顺序一致**，防止多线程下因指令重排序等优化导致的数据不一致。

### 缓存一致性问题的产生

多处理器系统中每个处理器有自己的缓存。多个处理器访问 / 修改同一共享内存时，一个处理器的修改可能不会立即被其它处理器看到，导致各自缓存中同一变量的值不一致，引发数据竞争、计算错误等。

### 四类屏障

| 屏障 | 保证 |
|---|---|
| `LoadLoad` | 屏障后的读不能重排到屏障前（读-读顺序） |
| `StoreStore` | 屏障前的写先于屏障后的写提交 |
| `LoadStore` | 屏障后的写不能重排到屏障前 |
| `StoreLoad` | 屏障前的写对所有处理器可见后，才执行屏障后的读写（**最重**，通常靠刷新写缓冲实现） |

### 别把"顺序"和"可见"混为一谈

这是最容易踩的坑：

- **写屏障（StoreStore）**：只保证"顺序"——若其它处理器看到了屏障**之后**的写（y），那么屏障**之前**的写（x）一定已可见；但它**不会让写立即生效**，跨处理器的即时可见性仍依赖 `StoreLoad` / 全屏障 / volatile；
- **读屏障（LoadLoad）**：只保证读的顺序——屏障后的读不会被重排到屏障前。它**不负责**让其它处理器的写变得可见；"读到之前写的结果"是 `StoreLoad` / 全屏障 / volatile 的职责。别误以为它能刷新缓存；
- **全屏障（Full）**：兼具读写屏障功能，保证屏障之前的所有内存操作都在之后的操作之前完成，最强但也最贵（金融、航天等强一致场景才用得上）。

# volatile 与 synchronized 的内存语义

## volatile

- **写 volatile 变量**：插入 `StoreStore` + `Store` + `StoreLoad`；
- **读 volatile 变量**：插入 `LoadLoad` + `Load` + `LoadStore`。

效果：保证**可见性**和**有序性**，但**不保证原子性**（`i++`、`check-then-act` 复合操作仍会错）。x86 上大部分屏障是空操作，真正花钱的主要是 `StoreLoad`（`mfence` / lock 前缀）。

## synchronized

- 原子性、可见性、有序性都保证；
- 语义上：**解锁 hb 后续对同一锁的加锁**，因此加锁时能看到解锁前所有写入。

> synchronized 的锁升级、字节码等细节见 [Synchorized.md](Synchorized.md)。

# 小结

1. **可见性问题从哪来？** CPU 多级缓存（缓存一致性）+ 指令重排序。
2. **happens-before 是什么？** JMM 定义的可见性规则，A hb B 则 A 的结果对 B 可见（是"可见"不是"先后"）。
3. **volatile 保证什么？** 可见性 + 有序性，不保证原子性。
4. **volatile 的底层？** 写加 StoreStore/StoreLoad，读加 LoadLoad/LoadStore，靠内存屏障实现。
5. **synchronized 保证什么？** 原子性、可见性、有序性（解锁 hb 加锁）。
6. **LockSupport 保证可见性吗？** 不保证，真正起作用的是 park/unpark 背后的 happens-before 和线程切换。
7. **线程切换为什么会影响可见性？** 切换时重新加载上下文与缓存，但也带来时间和缓存失效开销。
8. **StoreLoad 为什么最重？** 它要等前面所有写对其他处理器可见后才继续，通常靠刷新写缓冲实现。
