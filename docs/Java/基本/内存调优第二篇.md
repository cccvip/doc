# 内存调优方法论

抛出一个问题：为什么需要内存调优？你遇到过多少次非调优不可的情况？

工作几年下来，真正需要靠内存调优解决的场景其实不多，基本都是在问题暴露之后回头补。上一篇记录的是两次具体的排查过程，这一篇聊聊什么时候该介入、从哪里下手。

## 什么时候需要人工介入？

先明确一组"健康线"——满足这些通常**不需要**人工调优：

- Minor GC 执行时间 < 50ms；
- Minor GC 不太频繁，约 10 秒一次；
- Full GC 执行时间 < 1s；
- Full GC 不太频繁，约 10 分钟一次以上（即不要几分钟就来一次）。

反过来，一旦**明显超出**这些指标——比如 Full GC 达到秒级、频繁触发，或 Minor GC 又频繁又耗时——才需要人工介入调优。

## 为什么需要调优？

- young gc 次数太多有影响吗？有，但影响不太大；
- full gc 次数太多、太频繁有影响吗？肯定有，调优主要就是为了解决这个核心问题。

young 区存放的都是朝生夕死的对象。默认 15 次 GC 后仍存活的对象会进入 old 区，young:old 默认是 1:2，这套机制在大多数程序里是够用的。

old 区达到内存上限会立刻触发 full gc。full gc 的后果就是 STW，一旦超过 1s，就会带来大量请求超时，严重时直接 OOM、程序崩溃。

## 排查问题

完整流程和命令见 [JVM.md](JVM.md) 的「分析思路」一节，这里只记主线：

1. 确认现象：超时、CPU 高、内存涨、OOM；
2. `jps` 定位进程，`jstat -gcutil` + GC 日志看 YGC/FGC 和停顿；
3. `jmap -histo:live` / dump 看对象分布；
4. `jstack` + `top -Hp` 看是 GC 线程还是业务线程；
5. MAT 分析 dump，定位增长的类；
6. 回到代码，修复并复测。

关键判读：**Full GC 后老年代回落**多半是分配太快或堆小；**不回落**才是泄漏。

## 优化

- **架构调优**：选型决定这套系统能走多远，写代码时多考虑扩展性；
- **代码调优**：推荐用 arthas 排查，参考 [arthas user-case](https://github.com/alibaba/arthas/issues?page=1&q=label%3Auser-case)；
- **JVM 调优**：调整堆大小和比例、`-XX:+DisableExplicitGC`、设置元空间上限等；
- **数据库调优**：关注慢 SQL、索引；
- **操作系统调优**：文件句柄数、TCP 参数等。

## 总结

调优是一个枯燥但能带来些许成就感的流程。大部分问题最后都是代码问题，认真写代码、过一过脑子，比事后调参有用得多。
