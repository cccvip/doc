# 内存调优 Checklist（SOP）

> 这一篇不重复原理和命令，只回答四个问题：**要不要调、看什么、按什么顺序改、怎么验证。**
> 原理见 [JVM.md](JVM.md)，案例见 [内存调优.md](内存调优.md)。

## 0. 先记住一句话

**大部分"内存问题"最后都是代码问题，加内存只是把爆炸时间往后推。**

## 1. 要不要调？先过一遍健康线

| 指标 | 健康线 |
|---|---|
| Minor GC 耗时 | < 50ms |
| Minor GC 频率 | 约 10 秒一次 |
| Full GC 耗时 | < 1s |
| Full GC 频率 | 10 分钟一次以上 |

满足这些通常**不需要**人工调优。出现下面任意一条，才值得介入：

- Full GC 到了秒级，或几分钟一次；
- Minor GC 又频繁又慢（比如明显超过 100ms）；
- 老年代在 Full GC 后不回落；
- 已经出现 OOM，或接口大面积超时。

## 2. 看什么？指标 → 判断

| 现象 | 大概率原因 | 下一步 |
|---|---|---|
| Full GC 后老年代回落 | 分配太快 / 堆偏小 | 看分配速率、调堆 |
| Full GC 后老年代不降 | 内存泄漏 | dump + MAT |
| YGC 频繁、单次回收少 | 新生代小 / 对象创建快 | 调新生代、查代码 |
| FGC 频繁 | 老年代增长快 / 元空间 / `System.gc()` | 看老年代、Metaspace |
| 单次 STW 很长 | 堆大 + 单线程收集器 / 晋升多 | 换 G1 / ZGC、调阈值 |
| CPU 高但 GC 占比低 | 业务线程热点 | `jstack` / arthas |
| 线程数持续上涨 | 线程池 / 连接池泄漏 | 查池配置和关闭逻辑 |

关键判读：**Full GC 后老年代回落**多半是分配太快或堆小；**不回落**才是泄漏。

## 3. 按什么顺序改？

**代码 → 架构 → JVM → 数据库 → 操作系统**，越靠前收益越大。

### 3.1 代码

- 查无界缓存、静态集合、ThreadLocal 忘记 `remove()`；
- 查大对象、一次性全量查询、批量无上限；
- 用 arthas 的 `watch` / `trace` / `heapdump` 定位。

### 3.2 架构

- 缓存加过期、分页 / 流式处理、异步化；
- 不要把"内存不够"当成加机器能解决的事。

### 3.3 JVM

- 堆大小：`-Xms` / `-Xmx` 设成一样，避免动态扩缩；
- 新生代：`-Xmn` 或 `-XX:NewRatio`（默认 young:old = 1:2）；
- 晋升年龄：`-XX:MaxTenuringThreshold`，默认 15；
- 元空间：`-XX:MetaspaceSize` / `-XX:MaxMetaspaceSize`；
- 关闭显式 GC：`-XX:+DisableExplicitGC`；
- 收集器：低延迟选 G1，超大堆选 ZGC；
- 必开：`-XX:+HeapDumpOnOutOfMemoryError` + `-XX:HeapDumpPath`。

### 3.4 数据库

- 慢 SQL、索引、连接池上限；
- 大数据量分批处理。

### 3.5 操作系统

- 文件句柄数、TCP 参数、swap。

## 4. 常见误区

- **加内存治百病**：如果是泄漏，只是延后 OOM；
- **只盯 GC 参数**：很多问题是代码分配导致的；
- **抄别人的参数**：堆大小、收集器要和业务形态匹配；
- **不看 Full GC 后是否回落**：这是区分"泄漏"和"不够用"的关键；
- **把 STW 全算在 GC 头上**：也可能是 safePoint、偏向锁撤销等。

## 5. 改完怎么验证？

固定看四组数，前后对比：

1. YGC / FGC 次数；
2. YGC / FGC 单次耗时（GCT）；
3. Full GC 后老年代占用；
4. 接口 P99 和错误率。

> 没有前后对比的调优，等于没调。

## 6. 边界

这一篇只讲 GC / 内存。如果排查发现根因在 DB、下游 RPC 或线程池，就转去对应方向，不要继续在 JVM 参数上打转。
