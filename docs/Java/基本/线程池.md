# what

线程池是 Java 提供的线程复用机制：预先维护一批线程，任务提交到队列，由线程循环取出执行，避免频繁创建/销毁线程。

一句话核心：**ThreadPoolExecutor 就是一个「核心线程 + 任务队列 + 最大线程 + 拒绝策略」的组合。**

# 和 Executors 怎么选

| 工厂方法 | 底层配置 | 问题 |
|---|---|---|
| `newFixedThreadPool(n)` | core = max = n，`LinkedBlockingQueue` | 队列无界，可能 OOM，max 无效 |
| `newSingleThreadExecutor()` | core = max = 1，`LinkedBlockingQueue` | 队列无界 |
| `newCachedThreadPool()` | core = 0，max = `Integer.MAX_VALUE`，`SynchronousQueue` | 可能创建海量线程 |
| `newScheduledThreadPool(n)` | `DelayedWorkQueue` | 队列无界 |

结论：**生产上直接用 `ThreadPoolExecutor` 显式指定七个参数**，《阿里巴巴 Java 开发手册》也是这么要求的。

# 核心原理

## 七个参数

```java
public ThreadPoolExecutor(int corePoolSize,
                          int maximumPoolSize,
                          long keepAliveTime,
                          TimeUnit unit,
                          BlockingQueue<Runnable> workQueue,
                          ThreadFactory threadFactory,
                          RejectedExecutionHandler handler)
```

| 参数 | 含义 |
|---|---|
| `corePoolSize` | 核心线程数，默认常驻 |
| `maximumPoolSize` | 最大线程数 |
| `keepAliveTime` + `unit` | 超出核心数的空闲线程存活时间 |
| `workQueue` | 任务队列 |
| `threadFactory` | 线程工厂，建议自定义线程名 |
| `handler` | 拒绝策略 |

## 任务提交流程（背这一段）

1. 当前线程数 < `corePoolSize`：新建核心线程执行；
2. 否则尝试放入 `workQueue`；
3. 队列满了，且线程数 < `maximumPoolSize`：新建非核心线程执行；
4. 队列满且线程数达到 `maximumPoolSize`：执行拒绝策略。

关键顺序：**先入队，队列满了才扩容到 max**。所以用无界队列时，`maximumPoolSize` 永远不会生效。

## 线程复用

`Worker` 继承 AQS、实现 Runnable。线程启动后循环调用 `getTask()`：

- 从队列 `poll` / `take` 取任务；
- 取到就执行；
- 取不到就阻塞，或按 `keepAliveTime` 超时退出。

所以线程不会被销毁，而是一直复用。

## 线程池状态

状态和线程数打包在 `ctl` 里（高 3 位状态，低 29 位线程数）：

`RUNNING → SHUTDOWN → STOP → TIDYING → TERMINATED`

- `RUNNING`：接收新任务，处理队列；
- `SHUTDOWN`：不接新任务，处理完队列；
- `STOP`：不接新任务，不处理队列，中断执行中的任务；
- `TIDYING`：所有任务终止，准备清理；
- `TERMINATED`：终止完成。

# 八股速查

## 1. 为什么线程池要用 ThreadPoolExecutor 而不是 Executors？

`Executors` 的快捷工厂要么用无界队列（`FixedThreadPool`、`SingleThread`），要么允许无限线程（`CachedThreadPool`），都可能撑爆内存或线程数。手动创建才能把队列、线程数、拒绝策略都控制住。

## 2. 常见队列怎么选？

| 队列 | 特点 |
|---|---|
| `ArrayBlockingQueue` | 有界数组，推荐 |
| `LinkedBlockingQueue` | 默认无界（`Integer.MAX_VALUE`），慎用 |
| `SynchronousQueue` | 不存储，直接交给线程，配合大 max 使用 |
| `PriorityBlockingQueue` | 优先级，无界 |
| `DelayQueue` | 延迟任务 |

## 3. 四种拒绝策略

- `AbortPolicy`（默认）：抛 `RejectedExecutionException`；
- `CallerRunsPolicy`：交给提交任务的线程执行，起到反压作用；
- `DiscardPolicy`：静默丢弃；
- `DiscardOldestPolicy`：丢掉最老的任务再提交。

生产上一般选 `AbortPolicy` 或 `CallerRunsPolicy`，不要静默丢任务。

## 4. 线程数怎么设？

- CPU 密集：`N + 1`；
- IO 密集：`2N` 或 `N × (1 + 等待时间 / 计算时间)`；
- 最终以压测为准，别照抄公式。

## 5. shutdown 和 shutdownNow 的区别？

- `shutdown()`：不再接新任务，已提交的（含队列里的）会执行完；
- `shutdownNow()`：不再接新任务，中断正在执行的线程，并返回队列里没执行的任务。

## 6. submit 和 execute 的区别？

- `execute(Runnable)`：异常会抛给 `UncaughtExceptionHandler`；
- `submit(...)`：返回 `Future`，异常被包进 `Future`，不调用 `get()` 就看不到，容易被吞掉。

## 7. 核心线程会回收吗？

默认不会。设置 `allowCoreThreadTimeOut(true)` 后，核心线程空闲超过 `keepAliveTime` 也会退出。

## 8. 线程池能动态调整吗？

可以：`setCorePoolSize`、`setMaximumPoolSize`、`setRejectedExecutionHandler`。注意 `core <= max`，且缩容不会立刻终止正在执行的任务。

## 9. 线程池怎么监控？

`getPoolSize()`、`getActiveCount()`、`getQueue().size()`、`getCompletedTaskCount()`。配合自定义 `ThreadFactory` 命名线程，排查时才能对上业务。

## 10. 为什么先入队，而不是核心满了就扩容？

这是 ThreadPoolExecutor 的设计：优先复用队列缓冲，队列满了才认为「真的忙不过来」，再扩到 max。代价是无界队列会让 max 失效，所以队列必须有界。

# 实战场景

## 场景一：Web 请求处理

固定大小线程池 + 有界队列 + `CallerRunsPolicy`，过载时反压到 Tomcat 线程，避免任务无限堆积。

## 场景二：批量任务

分片提交，控制单批大小；用 `CompletableFuture` 组合结果。一定要传自定义线程池，别用默认的 `ForkJoinPool.commonPool()`。

## 场景三：异步解耦

下单后发消息、写日志等非核心链路异步化，用**独立线程池隔离**，避免拖垮主流程。

## 场景四：定时任务

`ScheduledThreadPoolExecutor`。注意 `scheduleAtFixedRate` 里任务抛异常会导致后续执行停止，务必在任务内部 try-catch。

## 标准创建模板

```java
new ThreadPoolExecutor(
    8,                                  // core
    16,                                 // max
    60, TimeUnit.SECONDS,               // keepAlive
    new ArrayBlockingQueue<>(1000),     // 有界队列
    new ThreadFactory() {               // 命名线程
        private final AtomicInteger i = new AtomicInteger(1);
        public Thread newThread(Runnable r) {
            return new Thread(r, "biz-pool-" + i.getAndIncrement());
        }
    },
    new ThreadPoolExecutor.CallerRunsPolicy()
);
```

## 场景五：Spring Cloud Feign 的两种调用模式

Feign 本身只是声明式 HTTP 客户端，**它不决定线程模型**；真正决定"调用在哪个线程上执行"的是隔离组件（旧版是 Hystrix，新版是 Resilience4j / Sentinel）。

| 模式 | 执行线程 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| 信号量隔离 | 调用方线程（不新建） | 无线程切换，ThreadLocal 天然能传 | 不能主动超时中断，慢调用占住调用线程 | 下游快、RT 稳定 |
| 线程池隔离 | 独立线程池 | 可主动超时、故障隔离、可异步 | 线程切换开销；要配池；ThreadLocal 会丢 | 下游慢、需要熔断超时 |

### 源码视角：Hystrix 到底在哪建线程

**1. Feign 侧**

- 开启 `feign.hystrix.enabled=true` 后，`HystrixTargeter` 会用 `HystrixFeign.Builder` 包装目标；
- 每次调用进入 `HystrixInvocationHandler.invoke`，构造一个 `HystrixCommand`，再 `execute()` / `queue()` / `observe()`；
- `HystrixCommand` 只是"命令"，真正决定跑在哪由下面的隔离策略决定。

**2. Hystrix 侧**

`AbstractCommand.executeCommandWithSpecifiedIsolation()` 里按策略分支（伪代码，保留核心分支）：

```java
if (properties.executionIsolationStrategy().get() == ExecutionIsolationStrategy.THREAD) {
    // 提交到线程池，调用线程 Future.get() 等待
    Future<T> f = threadPool.getExecutor()
            .submit(new HystrixContextRunnable(...));
    return f.get(...);
} else {
    // SEMAPHORE：拿许可，在调用线程直接执行 run()
    if (executionSemaphore.tryAcquire()) {
        return executeCommandAndObserve(...);
    }
}
```

**3. 线程池长什么样**

`HystrixThreadPoolDefault` 底层是 `ThreadPoolExecutor`：

- 每个 `HystrixThreadPoolKey` 一个池，默认按 Feign 客户端（groupKey）分组；
- 默认 `core = max = coreSize`，所以通常只关注 `coreSize`（新版本可通过 `maximumSize` 调整最大线程数）；
- `maxQueueSize = -1` 用 `SynchronousQueue`，否则用 `LinkedBlockingQueue`；
- 队列满后由 `queueSizeRejectionThreshold` 决定何时拒绝；
- 空闲线程 `keepAliveTimeMinutes` 默认 1 分钟。

**4. 关键细节：只传 HystrixRequestContext**

`HystrixContextRunnable` 会把父线程的 `HystrixRequestContext` 带到工作线程，但**不会**自动带 MDC、traceId、业务 `UserContext`。

### 两种模式的完整配置

THREAD：

```yaml
feign:
  hystrix:
    enabled: true

hystrix:
  command:
    default:
      execution:
        isolation:
          strategy: THREAD
          thread:
            timeoutInMilliseconds: 800
  threadpool:
    default:
      coreSize: 20
      maxQueueSize: 200
      queueSizeRejectionThreshold: 150
      keepAliveTimeMinutes: 1
```

按客户端细化线程池：

```yaml
hystrix:
  threadpool:
    ProductClient:
      coreSize: 20
    OrderClient:
      coreSize: 10
```

SEMAPHORE：

```yaml
hystrix:
  command:
    default:
      execution:
        isolation:
          strategy: SEMAPHORE
          semaphore:
            maxConcurrentRequests: 100
```

### 容量怎么估

`coreSize ≈ 下游 QPS × 平均 RT（秒）× 冗余系数`。

例：调用商品服务 500 QPS、平均 RT 20ms：

- 并发 ≈ 500 × 0.02 = 10；
- 留 2 倍冗余 → `coreSize = 20`；
- `maxQueueSize` 不宜大：任务在队列里排队，超时后即使执行也大概率失败；Hystrix 官方建议用小的队列或 `SynchronousQueue`。

信号量同理：`maxConcurrentRequests ≈ QPS × RT × 冗余`。

### ThreadLocal 会丢

线程池隔离下，调用发生在另一个线程：`UserContext`、`traceId`、MDC 都拿不到。解法：

1. 自定义 `HystrixConcurrencyStrategy`，重写 `wrapCallable`，把上下文复制到工作线程；
2. 用 `TransmittableThreadLocal` + `TtlExecutors` 装饰线程池；
3. 不需要主动超时的话，直接改信号量隔离，调用仍在原线程，上下文天然不丢。

### 常见失败表现

| 现象 | 原因 |
|---|---|
| `could not be queued for execution` / `RejectedExecutionException` | 线程池和队列都满了 |
| `HystrixTimeoutException` / `timed-out` | 超过 `timeoutInMilliseconds`，触发 fallback |
| 熔断直接走 fallback | 错误率 / 并发超过阈值，`HystrixCircuitBreaker` 打开 |
| 下游拿不到用户 / traceId | 线程池隔离丢了 ThreadLocal |
| 线程数暴涨 | 每个依赖一个池，池数量 × coreSize |

### 和业务线程池的关系

- 业务线程池（Tomcat / 自建）负责处理请求；
- Feign 的隔离线程池是在业务线程之外**再加一层**；
- 总线程数 = 业务池 + 各依赖隔离池，估算容量时不能只算一层。

### 别混淆连接池

Feign 底层的 Apache HttpClient / OkHttp 还有自己的**连接池**（`maxConnections`、`maxConnectionsPerRoute`），它和 Hystrix 的线程池是两回事：一个管连接复用，一个管调用线程。

> 版本提示：Spring Cloud Netflix Hystrix 已进入维护模式，新版一般用 Resilience4j（`SemaphoreBulkhead` / `ThreadPoolBulkhead`）或 Sentinel（信号量风格，不额外建线程池）。上面的两种模式和容量估算方法仍然适用。

# 常见坑

1. **无界队列**：任务堆积到 OOM，`max` 形同虚设；
2. **父子任务用同一个池**：父任务等子任务，线程全被父任务占满 → 死锁；
3. **ThreadLocal 不清理**：线程复用导致上下文串号；
4. **异常被吞**：用 `submit` 却不 `get()`，任务失败无感知；
5. **线程不命名**：排查问题时线程栈全是 `pool-1-thread-x`；
6. **关闭不等待**：`shutdown()` 后没 `awaitTermination`，任务可能被中断；
7. **拒绝了不处理**：自定义拒绝策略里直接吞掉任务，等于静默丢单。
