我相信大家都看过不少线程池的文章，而且它基本上是面试必问的。如果你看完很多篇还是一知半解，那希望本文能让你真正搞明白它。

线程池的重要性不必多说，很多线上问题都是没用对线程池导致的——即使只为了谋生，这也是绕不过去的知识。本文的思路是：先把设计思想和几个关键概念讲清楚，再把 `execute`、`addWorker`、`getTask` 这几个核心方法**一行一行带中文注释过一遍**。至于又长又少用的方法，我会明确说"留给读者"，不在这儿抄源码浪费篇幅。

> 本文有点长，建议对着 JDK 源码一起看（Java7/Java8 都行）。如果你只是准备面试，可以直接滑到最后的**小结**。

# 总览

线程池要解决的问题只有一句话：**复用线程**。预先养一批线程，任务丢进队列，线程循环取出来执行，免得频繁创建/销毁线程。

先看继承关系，从最简单的一层往下：

```text
Executor                 // 只有 execute(Runnable)
  └─ ExecutorService     // 加了一堆方法：submit / shutdown / invokeAll ...
       └─ AbstractExecutorService   // 实现了 submit、invokeAll 等
            └─ ThreadPoolExecutor   // 本文主角
```

- `Executor`：最顶层，就一个 `void execute(Runnable command)`，代表"提交一个任务"；
- `ExecutorService`：**平时我们用的就是它**，有提交、关闭、批量执行等能力；
- `AbstractExecutorService`：抽象类，实现了几个通用方法，但**它自己不干活**，最终都还是调 `execute`；
- `ThreadPoolExecutor`：真正的实现，下面全部围绕它。

还有两个概念要先记住，不然看源码会绕晕：

- **任务是 Runnable**（内部变量名 `task` 或 `command`），**线程是 Worker**。线程池里出现 `new Thread(r)` 时，那个 `r` 不是"要启动的线程"，而是"这个线程要执行的任务"；
- 提交任务时，如果是需要结果（`submit`），会先把 Runnable 包装成 **FutureTask**。`FutureTask` 这个名字拆开就是：首先它是个 Task，然后具有 Future 语义——将来能拿到结果。

> 一句话记：需要结果用 `submit`（返回 Future），不需要结果用 `execute`。

# 七个参数

几乎所有的工厂方法，最后都会导向这个构造方法：

```java
public ThreadPoolExecutor(int corePoolSize,        // 核心线程数，默认常驻（会一直复用，不回收）
                          int maximumPoolSize,     // 最大线程数
                          long keepAliveTime,      // 超出核心数的空闲线程能活多久
                          TimeUnit unit,           // keepAliveTime 的时间单位
                          BlockingQueue<Runnable> workQueue,   // 任务队列
                          ThreadFactory threadFactory,        // 线程工厂，建议自定义线程名
                          RejectedExecutionHandler handler)   // 拒绝策略
{
    // ...... 一堆参数校验后，逐个赋值，没什么好看的
}
```

重点关注 `corePoolSize` 和 `maximumPoolSize` 之间那段范围：`[core, max]` 之间的线程是"临时工"，空闲超过 `keepAliveTime` 就会被回收。核心线程默认不回收，但调用 `allowCoreThreadTimeOut(true)` 后连核心线程也能回收。

# ctl：一个 int 装下状态和线程数

看 `execute` 之前，必须先看懂 `ctl`，否则后面代码里到处是 `workerCountOf(c)` 会一脸懵。

Doug Lea 用一个 32 位整数同时存**线程池状态（高 3 位）**和**线程数（低 29 位）**：

```java
private final AtomicInteger ctl = new AtomicInteger(ctlOf(RUNNING, 0));

// COUNT_BITS = 29，因为高 3 位留给状态
private static final int COUNT_BITS = Integer.SIZE - 3;
// 低 29 位全是 1 => 最大线程数 2^29-1 ≈ 5 亿，够用了
private static final int CAPACITY = (1 << COUNT_BITS) - 1;

// 5 种状态，用高 3 位表示。注意 RUNNING 是 -1，所以它是所有状态里最小的
private static final int RUNNING    = -1 << COUNT_BITS; // 111 000...
private static final int SHUTDOWN   =  0 << COUNT_BITS; // 000 000...
private static final int STOP       =  1 << COUNT_BITS; // 001 000...
private static final int TIDYING    =  2 << COUNT_BITS; // 010 000...
private static final int TERMINATED =  3 << COUNT_BITS; // 011 000...

// 取状态：把低 29 位抹掉
private static int runStateOf(int c)     { return c & ~CAPACITY; }
// 取线程数：把高 3 位抹掉
private static int workerCountOf(int c)  { return c & CAPACITY; }
```

五个状态的含义和流转（记住前两个就够面试用了）：

- `RUNNING`：最正常，接收新任务、也处理队列里的任务；
- `SHUTDOWN`：不接新任务了，但**继续把队列里的任务处理完**（调用 `shutdown()` 进入）；
- `STOP`：不接新任务，队列里的也不处理，还**中断正在执行的任务**（调用 `shutdownNow()` 进入）；
- `TIDYING`：任务都清空了，线程数也为 0，准备收尾（会执行钩子 `terminated()`）；
- `TERMINATED`：`terminated()` 执行完，池子彻底结束。

> `RUNNING` 是 -1，比谁都小。所以判断"还在跑"用 `c < SHUTDOWN` 就很自然。

# execute：任务提交主流程

各种提交方法最终都落到它身上，这是**最重要的一段源码**：

```java
public void execute(Runnable command) {
    if (command == null)
        throw new NullPointerException();

    int c = ctl.get();

    // 分支一：线程数还不到核心线程数，直接建个核心线程来跑它
    if (workerCountOf(c) < corePoolSize) {
        if (addWorker(command, true))   // true 表示以 corePoolSize 为界
            return;
        c = ctl.get();                  // 建失败了，重读 ctl
    }

    // 分支二：核心线程满了，把任务丢进队列
    if (isRunning(c) && workQueue.offer(command)) {
        int recheck = ctl.get();
        // 再检查一次：入队后线程池可能刚好被关闭了，那就把任务撤出来并拒绝
        if (! isRunning(recheck) && remove(command))
            reject(command);
        // 池子还在跑，但线程数是 0，说明没有线程能消费队列了，赶紧补一个
        else if (workerCountOf(recheck) == 0)
            addWorker(null, false);
    }

    // 分支三：队列也满了，尝试扩到 maximumPoolSize
    else if (!addWorker(command, false)) // false 表示以 maximumPoolSize 为界
        reject(command);                 // 扩不动了，执行拒绝策略
}
```

把这段话背下来：**核心满了先入队，队列满了才扩到 max，max 也满了才拒绝**。

这里有个常被误解的点——很多人以为"线程数在 `[core, max]` 之间就创建新线程"，其实从上面三个分支可以看出，**队列没满就轮不到扩容**。所以：

> **用的队列如果是无界的（比如默认的 `LinkedBlockingQueue`），`maximumPoolSize` 永远生效不了**，因为队列根本不会满。这也是为什么生产上队列必须有界。

# addWorker：真正创建线程的地方

`execute` 里反复调的就是它。第一个参数是要交给新线程执行的任务（可以为 null），第二个参数决定以 `corePoolSize` 还是 `maximumPoolSize` 为上限：

```java
private boolean addWorker(Runnable firstTask, boolean core) {
    retry:
    for (;;) {
        int c = ctl.get();
        int rs = runStateOf(c);

        // 池子已经关了，就别建了。唯一例外：SHUTDOWN 状态下、没有新任务、且队列非空
        // 这对应 SHUTDOWN 的语义：不接新任务，但要把队列里的活儿干完
        if (rs >= SHUTDOWN &&
            ! (rs == SHUTDOWN && firstTask == null && ! workQueue.isEmpty()))
            return false;

        // 内层循环：用 CAS 把线程数 +1（并发下可能失败，失败就重试）
        for (;;) {
            int wc = workerCountOf(c);
            if (wc >= CAPACITY || wc >= (core ? corePoolSize : maximumPoolSize))
                return false;                    // 到上限了，不建
            if (compareAndIncrementWorkerCount(c))
                break retry;                     // +1 成功，跳出准备建线程
            c = ctl.get();                       // +1 失败，重读 ctl
            if (runStateOf(c) != rs)
                continue retry;                  // 状态被别人改了，回到外层
        }
    }

    boolean workerStarted = false;
    boolean workerAdded = false;
    Worker w = null;
    try {
        w = new Worker(firstTask);               // Worker 的构造里会用 ThreadFactory 造线程
        final Thread t = w.thread;
        if (t != null) {
            final ReentrantLock mainLock = this.mainLock;
            mainLock.lock();                     // 全局锁，保护 workers 集合
            try {
                int rs = runStateOf(ctl.get());
                if (rs < SHUTDOWN ||
                    (rs == SHUTDOWN && firstTask == null)) {
                    if (t.isAlive())             // 线程不能是已经启动过的
                        throw new IllegalThreadStateException();
                    workers.add(w);              // 加入 workers 集合
                    int s = workers.size();
                    if (s > largestPoolSize)     // 记录历史峰值，监控用
                        largestPoolSize = s;
                    workerAdded = true;
                }
            } finally {
                mainLock.unlock();
            }
            if (workerAdded) {
                t.start();                       // 启动线程
                workerStarted = true;
            }
        }
    } finally {
        // 线程没启动成功，要把前面 +1 的线程数减回去，做清理
        if (! workerStarted)
            addWorkerFailed(w);
    }
    return workerStarted;
}
```

`addWorkerFailed` 没什么内容，就是把 worker 从集合里删掉、线程数 -1，**留给读者自己看**。

关键是搞懂 `Worker` 这个内部类——它把"一条线程 + 它的第一个任务"包了起来：

```java
private final class Worker extends AbstractQueuedSynchronizer implements Runnable {
    final Thread thread;              // 真正的线程，任务靠它跑
    Runnable firstTask;               // 启动后要执行的第一个任务（可以为 null）
    volatile long completedTasks;     // 这个线程一共完成了多少任务

    Worker(Runnable firstTask) {
        setState(-1);                 // 先禁止中断，runWorker 里再放开
        this.firstTask = firstTask;
        this.thread = getThreadFactory().newThread(this);  // 把自己包成 Thread
    }

    public void run() {
        runWorker(this);              // 线程一启动，就进 runWorker
    }
    // ...... 其余是 AQS 的独占锁方法，用来控制"这个线程此刻能不能被中断"
}
```

> 看到 `AbstractQueuedSynchronizer` 是不是有点眼熟？AQS 在并发包里无处不在，后面 [ReentrantLock](ReentrantLock.md) 还会专门讲它。

# runWorker 和 getTask：线程是怎么复用的

线程启动后进入 `runWorker`，核心就是一个 while 循环，不断取任务、执行：

```java
final void runWorker(Worker w) {
    Thread wt = Thread.currentThread();
    Runnable task = w.firstTask;      // 先看有没有"自带"的第一个任务
    w.firstTask = null;               // 用完就置空，避免重复执行
    w.unlock();                       // 放开中断（对应构造里的 setState(-1)）

    boolean completedAbruptly = true;
    try {
        // 关键在这：task 取完（返回 null）才退出循环
        while (task != null || (task = getTask()) != null) {
            w.lock();
            // 如果池子已经到 STOP 了，就中断当前线程
            if ((runStateAtLeast(ctl.get(), STOP) ||
                 (Thread.interrupted() && runStateAtLeast(ctl.get(), STOP))) &&
                !wt.isInterrupted())
                wt.interrupt();
            try {
                beforeExecute(wt, task);   // 钩子方法，子类可扩展
                Throwable thrown = null;
                try {
                    task.run();            // 终于执行任务了
                } catch (RuntimeException x) {
                    thrown = x; throw x;
                } catch (Error x) {
                    thrown = x; throw x;
                } catch (Throwable x) {
                    thrown = x; throw new Error(x);   // 不允许抛 Throwable，转成 Error
                } finally {
                    afterExecute(task, thrown);       // 钩子方法
                }
            } finally {
                task = null;
                w.completedTasks++;       // 完成数 +1
                w.unlock();
            }
        }
        completedAbruptly = false;
    } finally {
        // 走到这里：要么队列空了该关闭，要么任务执行时抛异常了。
        // 这个方法负责善后（线程数 -1、必要时补建线程），限于篇幅不展开，读者自行翻源码
        processWorkerExit(w, completedAbruptly);
    }
}
```

**这就是"线程复用"的真相**：线程执行完一个任务不退出，而是回到 `while` 循环里继续 `getTask()` 取下一个，取不到才停。

`getTask()` 是整段里最精彩的方法，行数不多，却把"要不要阻塞、要不要超时、要不要返回 null（=关闭线程）"全考虑到了：

```java
private Runnable getTask() {
    boolean timedOut = false;   // 上一次 poll 是不是超时了

    for (;;) {
        int c = ctl.get();
        int rs = runStateOf(c);

        // 池子 STOP 了，或者 SHUTDOWN 且队列已空 => 没有任务可做了，返回 null（线程将退出）
        if (rs >= SHUTDOWN && (rs >= STOP || workQueue.isEmpty())) {
            decrementWorkerCount();   // 线程数 -1
            return null;
        }

        int wc = workerCountOf(c);
        // 是否允许这个线程超时回收：允许回收核心线程，或者当前线程数已超过核心数
        boolean timed = allowCoreThreadTimeOut || wc > corePoolSize;

        // 线程数超过 max（比如调小了 max），或已经超时 => 该关掉这个线程了
        if ((wc > maximumPoolSize || (timed && timedOut))
            && (wc > 1 || workQueue.isEmpty())) {
            if (compareAndDecrementWorkerCount(c))
                return null;
            continue;
        }

        try {
            // 会被回收的线程用 poll（带超时），核心线程用 take（一直阻塞等任务）
            Runnable r = timed ?
                workQueue.poll(keepAliveTime, TimeUnit.NANOSECONDS) :
                workQueue.take();
            if (r != null)
                return r;
            timedOut = true;
        } catch (InterruptedException retry) {
            timedOut = false;   // 被中断，重来
        }
    }
}
```

> `getTask` 返回 null，就意味着"这个线程可以死了"。`runWorker` 的 while 条件一为 false，就退出循环去 `processWorkerExit`。

# 拒绝策略

池子和队列都满了，就走 `reject(command)`，它会调用你传进来的 `RejectedExecutionHandler`。JDK 给了四个实现，可以直接用：

```java
// 默认策略：直接抛异常。宁可报错，也不悄悄丢任务
public static class AbortPolicy implements RejectedExecutionHandler {
    public void rejectedExecution(Runnable r, ThreadPoolExecutor e) {
        throw new RejectedExecutionException("Task " + r.toString() +
                                             " rejected from " + e.toString());
    }
}

// 交给"提交任务的那个线程"自己执行，形成反压，让上游慢下来
public static class CallerRunsPolicy implements RejectedExecutionHandler {
    public void rejectedExecution(Runnable r, ThreadPoolExecutor e) {
        if (!e.isShutdown()) {
            r.run();   // 谁提交谁跑
        }
    }
}

// 什么都不做，静默丢弃
public static class DiscardPolicy implements RejectedExecutionHandler {
    public void rejectedExecution(Runnable r, ThreadPoolExecutor e) { }
}

// 丢掉队列里排队最久（队头）的那个任务，再把当前任务塞进去
public static class DiscardOldestPolicy implements RejectedExecutionHandler {
    public void rejectedExecution(Runnable r, ThreadPoolExecutor e) {
        if (!e.isShutdown()) {
            e.getQueue().poll();
            e.execute(r);
        }
    }
}
```

生产上一般选 `AbortPolicy` 或 `CallerRunsPolicy`，**别用后两个静默丢弃**——任务丢了还不报错，排查起来能要命。

# Executors 的几个工厂

`Executors` 是工具类（注意类名带 s），里面都是静态方法。它很方便，但**生产环境不推荐直接用它**，原因看下面三个：

```java
// 固定大小：core = max = n，队列是无界的 LinkedBlockingQueue
public static ExecutorService newFixedThreadPool(int nThreads) {
    return new ThreadPoolExecutor(nThreads, nThreads,
                                  0L, TimeUnit.MILLISECONDS,
                                  new LinkedBlockingQueue<Runnable>());
}

// 单线程：本质就是 core = max = 1，队列同样无界
public static ExecutorService newSingleThreadExecutor() {
    return new FinalizableDelegatedExecutorService
        (new ThreadPoolExecutor(1, 1,
                                0L, TimeUnit.MILLISECONDS,
                                new LinkedBlockingQueue<Runnable>()));
}

// 来一个任务就开一个线程（空闲 60 秒回收），最大线程数是 Integer.MAX_VALUE
public static ExecutorService newCachedThreadPool() {
    return new ThreadPoolExecutor(0, Integer.MAX_VALUE,
                                  60L, TimeUnit.SECONDS,
                                  new SynchronousQueue<Runnable>());
}
```

问题一目了然：

| 工厂方法 | 隐患 |
|---|---|
| `newFixedThreadPool` / `newSingleThreadExecutor` | 队列无界 → 任务无限堆积，可能 OOM；`max` 也失去意义 |
| `newCachedThreadPool` | 最大线程数近乎无限 → 可能创建海量线程把系统拖垮 |
| `newScheduledThreadPool` | 队列同样无界 |

**所以生产上请直接用 `ThreadPoolExecutor` 显式指定七个参数**——《阿里巴巴 Java 开发手册》也是硬性要求的。

## 队列怎么选

- `ArrayBlockingQueue`：有界数组，**推荐**，配合合理的 max 用；
- `LinkedBlockingQueue`：默认无界（`Integer.MAX_VALUE`），慎用；
- `SynchronousQueue`：不存元素，来任务直接交给线程，配合大 max 用（`CachedThreadPool` 就是它）；
- `PriorityBlockingQueue` / `DelayQueue`：有优先级 / 延迟需求时用，但都是无界的。

## 线程数怎么设

- CPU 密集：`N + 1`（N 是核数）；
- IO 密集：`2N` 或 `N × (1 + 等待时间 / 计算时间)`；
- 这些都是经验公式，**最终以压测为准**，别照抄。

一个可以直接抄的模板：

```java
new ThreadPoolExecutor(
    8,                                  // core
    16,                                 // max
    60, TimeUnit.SECONDS,               // keepAlive
    new ArrayBlockingQueue<>(1000),     // 有界队列，这点最重要
    new ThreadFactory() {               // 给线程起个能认出来的名字
        private final AtomicInteger i = new AtomicInteger(1);
        public Thread newThread(Runnable r) {
            return new Thread(r, "biz-pool-" + i.getAndIncrement());
        }
    },
    new ThreadPoolExecutor.CallerRunsPolicy()
);
```

# 线程池在框架中的应用

前面我们把 `ThreadPoolExecutor` 从 `ctl` 一路拆到 `getTask`。你可能会问：这套东西除了自己 `new` 一个业务线程池，还有谁在用？

答案是——**到处都在用**。Spring 的 `ThreadPoolTaskExecutor`、Tomcat 处理请求的工作线程、`CompletableFuture` 的默认池、以及各种 RPC 框架的调用隔离，底层基本都是 `ThreadPoolExecutor`。这里挑一个最能说明问题的例子：**Feign 的调用隔离**。

先说结论：**Feign 本身只是声明式 HTTP 客户端，它不决定线程模型**；真正决定"调用在哪个线程上执行"的是隔离组件（老版本是 Hystrix，新版本一般换成 Resilience4j / Sentinel）。而它的"线程池隔离"，底层建的就是我们前面读的那个 `ThreadPoolExecutor`。

| 模式 | 执行线程 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| 信号量隔离 | 调用方线程（不新建） | 无线程切换，ThreadLocal 天然能传 | 不能主动超时中断，慢调用占住调用线程 | 下游快、RT 稳定 |
| 线程池隔离 | 独立线程池 | 可主动超时、故障隔离、可异步 | 线程切换有开销；要配池；ThreadLocal 会丢 | 下游慢、需要熔断超时 |

线程是在哪儿切出去的？走一遍调用链就清楚了（伪代码，保留核心分支）：

```java
// Feign 侧：开启 feign.hystrix.enabled=true 后，每次调用都会构造一个 HystrixCommand
// Hystrix 侧：AbstractCommand.executeCommandWithSpecifiedIsolation() 里按隔离策略分支
if (properties.executionIsolationStrategy().get() == ExecutionIsolationStrategy.THREAD) {
    // 线程池模式：把任务 submit 到独立线程池，调用线程 Future.get() 等待
    // 注意这里的 submit / Future.get，就是前面讲过的"提交任务 + 获取结果"
    Future<T> f = threadPool.getExecutor().submit(new HystrixContextRunnable(...));
    return f.get(...);
} else {
    // 信号量模式：拿许可，直接在调用线程上执行，不新建线程
    if (executionSemaphore.tryAcquire()) {
        return executeCommandAndObserve(...);
    }
}
```

**那个 `threadPool.getExecutor()` 返回的，正是一个 `ThreadPoolExecutor`。** 对照前面那七个参数看它怎么配的：

- 每个 `HystrixThreadPoolKey` 一个池（默认按 Feign 客户端分组），这就是我们说的"池子隔离"；
- `core = max = coreSize`——没有 `[core, max]` 的弹性区间，所以它其实只关心 `coreSize` 一个参数；
- `maxQueueSize = -1` 时用 `SynchronousQueue`，否则用 `LinkedBlockingQueue`；队列满了由 `queueSizeRejectionThreshold` 提前拒绝，走的正是前面那套**拒绝策略**。

看下来你会发现：Hystrix 的隔离池并没有发明什么新东西，它只是把我们前面读过的参数，按"调用隔离"的诉求重新配了一遍。

> 两个容易踩的点：① 线程池隔离下，调用发生在另一个线程，`UserContext`、`traceId`、MDC 全都会丢（正是前面"ThreadLocal 不清理"那个坑的放大版），解法是自定义 `HystrixConcurrencyStrategy` 在 `wrapCallable` 里复制上下文，或用 `TransmittableThreadLocal` + `TtlExecutors`；② 容量按 `coreSize ≈ 下游 QPS × 平均 RT × 冗余` 估，队列别开大——排队超时的任务执行了也大概率失败。这两点是 Hystrix 自身的调参话题，跟线程池原理无关，就不在这儿展开了。

> 版本提示：Spring Cloud Netflix Hystrix 已进入维护模式，新版一般用 Resilience4j（`SemaphoreBulkhead` / `ThreadPoolBulkhead`）或 Sentinel；上面的两种模式和估算思路仍然适用。

理解了这段，下面这些坑基本就不会踩了：

# 常见坑

1. **用无界队列**：任务堆到 OOM，`max` 形同虚设；
2. **父子任务共用一个池**：父任务等子任务，线程全被父任务占满 → 死锁；
3. **ThreadLocal 不清理**：线程复用导致上下文串号（尤其配合上面的线程池隔离）；
4. **异常被吞**：用 `submit` 却不 `get()`，任务失败毫无感知；
5. **线程不命名**：出问题一看线程栈全是 `pool-1-thread-x`，对不上业务；
6. **关闭不等待**：`shutdown()` 后没 `awaitTermination`，任务可能被执行到一半就被中断；
7. **拒绝了不处理**：自定义拒绝策略里直接吞任务，等于静默丢单。

# 小结

我一向不太喜欢写总结，因为该说的正文里都说了。不过考虑到很多读者是冲着面试来的，这里还是列一份清单，赶时间的可以直接看这一节。

1. **线程池的关键属性有哪些？** `corePoolSize`、`maximumPoolSize`、`workQueue`、`keepAliveTime`、`handler`。`[core, max]` 之间的线程空闲超时会回收，核心线程默认不回收（可 `allowCoreThreadTimeOut(true)` 打开）。
2. **任务提交流程？** 线程数 < core → 建核心线程；否则入队；队列满且 < max → 建非核心线程；队列满且已达 max → 拒绝策略。
3. **为什么要用 ThreadPoolExecutor 而不是 Executors？** 前者能显式控制队列、线程数、拒绝策略；后者的工厂要么无界队列（可能 OOM），要么无限线程（可能拖垮系统）。
4. **为什么先入队、而不是核心满了就扩容？** 这是设计取舍：优先用队列缓冲，队列满了才认为"真忙不过来"。代价是无界队列会让 max 失效，所以队列必须有界。
5. **`shutdown` 和 `shutdownNow` 区别？** 前者不接新任务但把队列里的执行完；后者不接新任务、不处理队列，并中断正在执行的任务，返回没执行的任务列表。
6. **`submit` 和 `execute` 区别？** `execute` 的异常抛给 `UncaughtExceptionHandler`；`submit` 返回 Future，异常被包进 Future，不 `get()` 就看不到。
7. **线程是怎么复用的？** `Worker` 就是个带 AQS 的 Runnable，线程启动后进 `runWorker` 的 while 循环，反复 `getTask()` 取任务，取不到才退出。
8. **核心线程会回收吗？** 默认不会；`allowCoreThreadTimeOut(true)` 后，空闲超过 `keepAliveTime` 也会退出。
9. **能动态调整吗？** 可以：`setCorePoolSize`、`setMaximumPoolSize`、`setRejectedExecutionHandler`。注意 `core <= max`，且缩容不会立刻终止正在执行的任务。
10. **怎么监控？** `getPoolSize()`、`getActiveCount()`、`getQueue().size()`、`getCompletedTaskCount()`，配合自定义 `ThreadFactory` 命名线程。
