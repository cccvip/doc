我们平时写 Spring Boot，启动就是一行 `SpringApplication.run(ApiApplication.class, args)`。但这一行里到底发生了什么，很多人只有一个模糊印象：创建容器、扫描 Bean、启动 Tomcat。真到面试被问"Web 服务器是在哪一步起来的、`@PostConstruct` 和 Runner 谁先执行"，就容易卡住。

这篇我们跟着 `SpringApplication.run` 的源码走一遍，从 main 方法一直看到应用 ready。源码只保留关键行，省略的部分会直接标出来。

> 基于 Spring Boot 2.5.x。不同版本方法签名略有差异，主流程一致。

# 从 main 方法说起

```java
@SpringBootApplication
public class ApiApplication {
    public static void main(String[] args) {
        SpringApplication.run(ApiApplication.class, args);
    }
}
```

`SpringApplication.run` 先创建一个 `SpringApplication`，再调用实例的 `run`：

```java
public static ConfigurableApplicationContext run(Class<?> primarySource, String... args) {
    return new SpringApplication(primarySource).run(args);
}
```

构造方法里做了三件事：

```java
public SpringApplication(ResourceLoader resourceLoader, Class<?>... primarySources) {
    this.primarySources = new LinkedHashSet<>(Arrays.asList(primarySources));

    // ① 根据 classpath 推断应用类型：SERVLET / REACTIVE / NONE
    this.webApplicationType = WebApplicationType.deduceFromClasspath();

    // ② 从 spring.factories 加载初始化器和监听器
    setInitializers((Collection) getSpringFactoriesInstances(ApplicationContextInitializer.class));
    setListeners((Collection) getSpringFactoriesInstances(ApplicationListener.class));

    // ③ 推断 main 方法所在类
    this.mainApplicationClass = deduceMainApplicationClass();
}
```

`webApplicationType` 决定了后面创建哪种 ApplicationContext：

| 类型 | 判断条件 | 容器 |
|---|---|---|
| `SERVLET` | 有 `DispatcherServlet` 和 `Servlet` | `AnnotationConfigServletWebServerApplicationContext` |
| `REACTIVE` | 只有 WebFlux 的 `DispatcherHandler` | `AnnotationConfigReactiveWebServerApplicationContext` |
| `NONE` | 都没有 | `AnnotationConfigApplicationContext` |

`initializers` 和 `listeners` 是从 `spring.factories` 里读出来的扩展点，后面会在不同阶段回调。

# 准备 Environment

进入 `run` 之后，第一件正事是准备 `Environment`：

```java
private ConfigurableEnvironment prepareEnvironment(SpringApplicationRunListeners listeners,
        ApplicationArguments applicationArguments) {

    // ① 创建 Environment（Servlet 应用是 StandardServletEnvironment）
    ConfigurableEnvironment environment = getOrCreateEnvironment();

    // ② 配置：命令行参数、profile 等
    configureEnvironment(environment, applicationArguments.getSourceArgs());
    ConfigurationPropertySources.attach(environment);

    // ③ 发布 environmentPrepared 事件，application.yml 在这一步加载
    listeners.environmentPrepared(environment);

    // ④ 把 spring.main.* 绑定到 SpringApplication
    bindToSpringApplication(environment);

    return environment;
}
```

为什么这一步要放在最前面？因为后面创建容器、决定 Web 类型、加载自动配置，都要读配置。`application.yml`、`application-prod.yml`、命令行参数、环境变量，都是在这一步合并进 `Environment` 的。

# 创建 ApplicationContext

有了 Environment，接着创建容器：

```java
protected ConfigurableApplicationContext createApplicationContext() {
    return this.applicationContextFactory.create(this.webApplicationType);
}
```

根据前面的 `webApplicationType`，创建对应的容器。注意：**这时候容器是空的**，里面还没有 BeanDefinition，更没有 Bean 实例。

# prepareContext：把主配置类交给容器

容器创建出来之后，要先把 Environment、初始化器、主配置类交给它：

```java
private void prepareContext(ConfigurableApplicationContext context,
        ConfigurableEnvironment environment, SpringApplicationRunListeners listeners,
        ApplicationArguments applicationArguments) {

    // ① 设置 Environment
    context.setEnvironment(environment);

    // ② 应用初始化器：在 refresh 之前对容器做定制
    applyInitializers(context);

    // ③ 发布 contextPrepared 事件
    listeners.contextPrepared(context);

    // ④ 注册启动参数等特殊 Bean
    context.getBeanFactory().registerSingleton("springApplicationArguments", applicationArguments);

    // ⑤ 把主配置类（ApiApplication）注册进容器
    load(context, getAllSources().toArray(new Object[0]));

    // ⑥ 发布 contextLoaded 事件
    listeners.contextLoaded(context);
}
```

到这一步，容器里只有主配置类的 BeanDefinition，**还没 refresh**。也就是说，`@ComponentScan`、`@EnableAutoConfiguration` 都还没有被解析。

# refresh：真正开始装配

`refreshContext` 会调用 `AbstractApplicationContext.refresh()`。从这里开始，我们进入容器的内部流程：

```java
public void refresh() throws BeansException, IllegalStateException {
    prepareRefresh();

    // ① 创建 BeanFactory
    ConfigurableListableBeanFactory beanFactory = obtainFreshBeanFactory();
    prepareBeanFactory(beanFactory);

    try {
        postProcessBeanFactory(beanFactory);

        // ② 执行 BeanFactoryPostProcessor：自动装配在这里
        invokeBeanFactoryPostProcessors(beanFactory);

        // ③ 注册 BeanPostProcessor
        registerBeanPostProcessors(beanFactory);

        initMessageSource();
        initApplicationEventMulticaster();

        // ④ 创建内嵌 Web 服务器（还没启动）
        onRefresh();

        registerListeners();

        // ⑤ 实例化所有非懒加载单例
        finishBeanFactoryInitialization(beanFactory);

        // ⑥ 启动 Web 服务器
        finishRefresh();
    }
    catch (BeansException ex) {
        destroyBeans();
        cancelRefresh(ex);
        throw ex;
    }
}
```

和启动流程关系最大的，是下面五步。

**第一步：`invokeBeanFactoryPostProcessors`**

`ConfigurationClassPostProcessor` 在这里解析 `@Configuration`、`@ComponentScan`、`@Import`，`@EnableAutoConfiguration` 引入的自动配置类也是在这一步被处理的。细节见 [starter.md](starter.md)。

**第二步：`registerBeanPostProcessors`**

把 `@Autowired`、AOP 等 `BeanPostProcessor` 注册进容器。它们要在 Bean 实例化之前就位，否则后面的注入和代理都赶不上。

**第三步：`onRefresh`**

Servlet 应用会在这里创建内嵌 Web 服务器：

```java
@Override
protected void onRefresh() {
    super.onRefresh();
    createWebServer();   // 创建 Tomcat / Jetty / Undertow 对象
}
```

注意：这里只是**创建**服务器对象，端口还没有绑定，请求还进不来。

**第四步：`finishBeanFactoryInitialization`**

实例化所有非懒加载的单例。`@PostConstruct`、`InitializingBean.afterPropertiesSet()`、`init-method` 都在这一步执行。此时 Web 服务器已经创建，但还没启动。

**第五步：`finishRefresh`**

真正启动 Web 服务器：

```java
@Override
protected void finishRefresh() {
    super.finishRefresh();
    WebServer webServer = startWebServer();   // 绑定端口，开始接收请求
    if (webServer != null) {
        publishEvent(new ServletWebServerInitializedEvent(webServer, this));
    }
}
```

所以顺序是：

```text
onRefresh                        创建 WebServer，未绑定端口
finishBeanFactoryInitialization  实例化 Bean，@PostConstruct 在这里
finishRefresh                    启动 WebServer，开始接收请求
```

这也是为什么**在 `@PostConstruct` 里访问本机端口会失败**：服务器还没启动。

# Runner：启动后的最后一棒

`refresh()` 结束后，`run` 还会调用 `callRunners`：

```java
private void callRunners(ApplicationContext context, ApplicationArguments args) {
    List<Object> runners = new ArrayList<>();
    runners.addAll(context.getBeansOfType(ApplicationRunner.class).values());
    runners.addAll(context.getBeansOfType(CommandLineRunner.class).values());
    AnnotationAwareOrderComparator.sort(runners);

    for (Object runner : new LinkedHashSet<>(runners)) {
        if (runner instanceof ApplicationRunner) {
            callRunner((ApplicationRunner) runner, args);
        }
        if (runner instanceof CommandLineRunner) {
            callRunner((CommandLineRunner) runner, args);
        }
    }
}
```

`ApplicationRunner` 和 `CommandLineRunner` 都在**容器 refresh 完成、Web 服务器启动之后**执行，适合做缓存预热、调用本机接口、初始化业务数据。多个 Runner 之间用 `@Order` / `Ordered` 排序。

如果 Runner 里抛了异常，会走 `handleRunFailure`，整个应用启动失败。

# 启动完成

最后，`run` 会通知监听器：

```java
listeners.started(context);   // 容器已刷新、Runner 已执行
// ...
listeners.running(context);   // 应用已就绪
```

对应的事件是 `ApplicationStartedEvent` 和 `ApplicationReadyEvent`。如果中间任何一步抛异常，会发布 `ApplicationFailedEvent`，关闭已经创建的 context，再把异常抛出去。

# 小结

我一向不太喜欢写总结，因为该说的正文里都说了。不过考虑到很多读者是冲着面试来的，还是列成清单：

1. **启动分几步？** 构造 `SpringApplication` → 准备 Environment → 创建 Context → prepareContext → refresh → Runner → started/running。
2. **Web 类型怎么推断？** 有 `DispatcherServlet` + `Servlet` → SERVLET；只有 WebFlux → REACTIVE；否则 NONE。
3. **自动装配在启动流程的哪一步？** `refresh()` → `invokeBeanFactoryPostProcessors` → `ConfigurationClassPostProcessor`。
4. **Web 服务器什么时候创建、什么时候启动？** `onRefresh()` 创建，`finishRefresh()` 启动。
5. **Runner 和 `@PostConstruct` 的区别？** `@PostConstruct` 在 Bean 初始化阶段，服务器还没启动；Runner 在 `refresh()` 之后，服务器已启动。
6. **启动失败怎么处理？** `handleRunFailure` 发布 `ApplicationFailedEvent`、关闭 context、抛出异常。
7. **`ApplicationContextInitializer` 能做什么？** 在 refresh 之前操作 Environment / BeanFactory，不能拿 Bean。
