我们平时写 Spring Boot，启动就是一行 `SpringApplication.run(ApiApplication.class, args)`。但这一行里到底发生了什么，很多人只有一个模糊印象：创建容器、扫描 Bean、启动 Tomcat。真到面试被问"Web 服务器是在哪一步起来的、`@PostConstruct` 和 Runner 谁先执行"，就容易卡住。

这篇讲启动器的外层流程：`SpringApplication` 怎么读配置、怎么创建容器、什么时候执行 Runner。容器内部 `refresh()` 的十二步拆在 [refresh流程.md](refresh流程.md)，这里只保留概览和跳转。

# 先分清几个角色

不然后面很容易混：

- **`SpringApplication`**：启动器。负责读配置、创建 `ApplicationContext`、调用 `refresh()`、执行 Runner。它本身不是容器。
- **`ApplicationContext`**：容器。持有 `BeanFactory`、BeanDefinition、单例 Bean、事件发布器、资源加载器。
- **`BeanFactory`**：真正管理 BeanDefinition 和 Bean 实例的地方。`ApplicationContext` 在它外面加了事件、国际化、资源加载。
- **`Environment`**：配置环境。`application.yml`、profile、命令行参数、环境变量，最终都合并到这里。
- **`ApplicationContextInitializer`**：在 `refresh()` 之前对容器做编程式定制的扩展点。
- **`ApplicationListener`**：监听启动过程中的事件。
- **`ApplicationRunner` / `CommandLineRunner`**：容器 refresh 完成后执行的回调。

一句话：**`SpringApplication` 是启动器，`ApplicationContext` 是容器，`BeanFactory` 是容器里管 Bean 的那部分。**

# 从 main 方法开始

```java
@SpringBootApplication
public class ApiApplication {
    public static void main(String[] args) {
        SpringApplication.run(ApiApplication.class, args);
    }
}
```

`SpringApplication.run` 先创建一个 `SpringApplication`，再调用实例的 `run`：

```java
public static ConfigurableApplicationContext run(Class<?> primarySource, String... args) {
    return new SpringApplication(primarySource).run(args);
}
```

构造方法做三件事：

```java
public SpringApplication(ResourceLoader resourceLoader, Class<?>... primarySources) {
    this.primarySources = new LinkedHashSet<>(Arrays.asList(primarySources));

    // ① 根据 classpath 推断应用类型：SERVLET / REACTIVE / NONE
    this.webApplicationType = WebApplicationType.deduceFromClasspath();

    // ② 从 spring.factories 加载初始化器和监听器
    setInitializers((Collection) getSpringFactoriesInstances(ApplicationContextInitializer.class));
    setListeners((Collection) getSpringFactoriesInstances(ApplicationListener.class));

    // ③ 推断 main 方法所在类
    this.mainApplicationClass = deduceMainApplicationClass();
}
```

**为什么先推断 Web 类型？** 因为它决定了后面创建哪种 `ApplicationContext`，也决定了要不要启动内嵌 Web 服务器。判断逻辑很简单，看 classpath 上有没有特定的类：

- 有 `DispatcherServlet`、`Servlet` → `SERVLET`；
- 没有 Servlet、但有 WebFlux 的 `DispatcherHandler` → `REACTIVE`；
- 都没有 → `NONE`。

**为什么要加载 Initializer 和 Listener？** 它们是启动过程的扩展点。`ApplicationContextInitializer` 会在 `refresh()` 之前回调，让你有机会往容器里加 `BeanFactoryPostProcessor`、设置 profile；`ApplicationListener` 用来监听 `ApplicationStartedEvent`、`ApplicationReadyEvent` 这些事件。

**为什么要推断主类？** 主要用于日志和异常信息。启动失败时，日志里要能指出是哪个类启动的。

构造完成后，`SpringApplication` 手里有了应用类型、初始化器、监听器、主类。接下来进入实例的 `run`。

# 第一步：准备 Environment

`run` 里的第一件正事不是创建容器，而是准备 `Environment`。原因很直接：创建哪种容器、加载哪些自动配置、连不连数据库，都要先读配置。

```java
private ConfigurableEnvironment prepareEnvironment(SpringApplicationRunListeners listeners,
        ApplicationArguments applicationArguments) {

    // ① 创建 Environment
    ConfigurableEnvironment environment = getOrCreateEnvironment();

    // ② 把命令行参数、profile 等加进去
    configureEnvironment(environment, applicationArguments.getSourceArgs());
    ConfigurationPropertySources.attach(environment);

    // ③ 发布 environmentPrepared 事件：application.yml 在这一步加载
    listeners.environmentPrepared(environment);

    // ④ 把 spring.main.* 绑定到 SpringApplication
    bindToSpringApplication(environment);

    return environment;
}
```

这里有几个容易忽略的点。

**Environment 不止一个实现。** `getOrCreateEnvironment()` 会按应用类型创建：Servlet 应用是 `StandardServletEnvironment`，Reactive 是 `StandardReactiveWebEnvironment`，普通应用是 `StandardEnvironment`。它们的区别在于内置了哪些 `PropertySource`，比如 Servlet 环境会加入 `ServletConfig`、`ServletContext` 的参数。

**`application.yml` 不是一开始就在 Environment 里的。** `configureEnvironment` 只加了命令行参数和 profile；真正加载 `application.yml` 的是 `listeners.environmentPrepared` 触发的 `EnvironmentPostProcessor`，其中最重要的是 `ConfigFileApplicationListener`。它会按 `application.yml` → `application-{profile}.yml` 的顺序加载，并合并到 Environment。

**`bindToSpringApplication` 绑定的是 `spring.main.*`。** 比如 `spring.main.web-application-type`、`spring.main.lazy-initialization`、`spring.main.allow-circular-references`、`spring.main.banner-mode`。这些配置要在创建容器之前生效，所以必须在这里绑定。

**做完之后的状态**：Environment 里已经有了所有配置，但还没有任何 Bean。

# 第二步：创建 ApplicationContext

有了 Environment，接着创建容器：

```java
protected ConfigurableApplicationContext createApplicationContext() {
    return this.applicationContextFactory.create(this.webApplicationType);
}
```

`ApplicationContextFactory` 按类型创建：

| 类型 | 容器 | 多了什么能力 |
|---|---|---|
| `SERVLET` | `AnnotationConfigServletWebServerApplicationContext` | 持有内嵌 `WebServer`，支持 Servlet 作用域 |
| `REACTIVE` | `AnnotationConfigReactiveWebServerApplicationContext` | 响应式 Web 容器 |
| `NONE` | `AnnotationConfigApplicationContext` | 普通容器 |

以 Servlet 为例，它的继承链里有两个关键能力：

- `ServletWebServerApplicationContext`：持有 `WebServer` 字段，负责创建和启动内嵌服务器；
- `AnnotationConfigRegistry`：支持 `register(Class<?>...)` 注册注解配置类。

**做完之后的状态**：容器对象有了，但它是空的——没有 BeanDefinition，没有 Bean 实例，也没有 Web 服务器。真正的装配要等 `refresh()`。

# 第三步：prepareContext

容器创建出来后，不能直接 `refresh`，要先把 Environment、初始化器、主配置类交给它：

```java
private void prepareContext(ConfigurableApplicationContext context,
        ConfigurableEnvironment environment, SpringApplicationRunListeners listeners,
        ApplicationArguments applicationArguments) {

    // ① 设置 Environment
    context.setEnvironment(environment);

    // ② 应用初始化器：refresh 之前对容器做定制
    applyInitializers(context);

    // ③ 发布 contextPrepared 事件
    listeners.contextPrepared(context);

    // ④ 注册启动参数，让 Bean 可以注入 ApplicationArguments
    context.getBeanFactory().registerSingleton("springApplicationArguments", applicationArguments);

    // ⑤ 把主配置类（ApiApplication）注册进容器
    load(context, getAllSources().toArray(new Object[0]));

    // ⑥ 发布 contextLoaded 事件
    listeners.contextLoaded(context);
}
```

**`applyInitializers` 的时机很关键。** 它遍历前面加载的 `ApplicationContextInitializer`，逐个调用 `initialize(context)`。此时容器已经有了，但还没 refresh，所以初始化器可以往容器里加 `BeanFactoryPostProcessor`、设置 profile、注册自定义作用域；但它**不能 `getBean`**，因为 Bean 还没创建。

**`load` 只是注册 BeanDefinition，不解析注解。** 它把主配置类 `ApiApplication` 注册成一个 BeanDefinition。`@SpringBootApplication` 里的 `@ComponentScan`、`@EnableAutoConfiguration`，要等到 `refresh()` 阶段才处理。

**做完之后的状态**：容器里只有主配置类这一个 BeanDefinition，其他什么都没有。

# 第四步：refresh

`refreshContext` 会调用 `AbstractApplicationContext.refresh()`。这是容器真正"启动"的地方：创建 BeanFactory、执行后置处理器、实例化 Bean、启动 Web 服务器。

```java
private void refreshContext(ConfigurableApplicationContext context) {
    if (this.registerShutdownHook) {
        context.registerShutdownHook();   // 注册 JVM 关闭钩子
    }
    refresh(context);                     // 最终调用 context.refresh()
}
```

`refresh()` 内部有十二步，完整拆解见 [refresh流程.md](refresh流程.md)。这里只记住它做的五件事：

1. **准备 BeanFactory**：创建或获取 `DefaultListableBeanFactory`，注册 `Environment`、`ApplicationContext` 等基础设施；
2. **执行 BeanFactoryPostProcessor**：解析 `@Configuration`、`@ComponentScan`、`@Import`，自动装配在这一步发生；
3. **注册 BeanPostProcessor**：把 `@Autowired`、AOP 等后置处理器准备好；
4. **创建 Web 服务器**：`onRefresh()` 里创建 Tomcat/Jetty/Undertow，但还没绑定端口；
5. **实例化 Bean 并启动服务器**：`finishBeanFactoryInitialization()` 创建单例，`finishRefresh()` 启动 Web 服务器。

**做完之后的状态**：所有非懒加载单例已创建，AOP 代理已生成，Web 服务器已启动。

# 第五步：Runner

`refresh()` 结束后，`run` 还会执行 Runner：

```java
private void callRunners(ApplicationContext context, ApplicationArguments args) {
    List<Object> runners = new ArrayList<>();
    runners.addAll(context.getBeansOfType(ApplicationRunner.class).values());
    runners.addAll(context.getBeansOfType(CommandLineRunner.class).values());
    AnnotationAwareOrderComparator.sort(runners);

    for (Object runner : new LinkedHashSet<>(runners)) {
        if (runner instanceof ApplicationRunner) {
            callRunner((ApplicationRunner) runner, args);
        }
        if (runner instanceof CommandLineRunner) {
            callRunner((CommandLineRunner) runner, args);
        }
    }
}
```

`ApplicationRunner` 和 `CommandLineRunner` 的区别只在参数：前者拿 `ApplicationArguments`，后者拿原始 `String[]`。它们都在 **refresh 完成、Web 服务器启动之后**执行，适合做缓存预热、调用本机接口、初始化业务数据。

多个 Runner 之间用 `@Order` / `Ordered` 排序。如果 Runner 里抛了异常，会走 `handleRunFailure`，整个应用启动失败。

# 第六步：started / running

最后，`run` 会通知监听器：

```java
listeners.started(context);   // 容器已刷新、Runner 已执行
// ...
listeners.running(context);   // 应用已就绪
```

对应的事件：

- `ApplicationStartedEvent`：`refresh()` 完成、Runner 执行前；
- `ApplicationReadyEvent`：Runner 执行完、应用正式 ready。

如果中间任何一步抛异常，会走 `handleRunFailure`：发布 `ApplicationFailedEvent`、关闭已经创建的 context、把异常抛出去。

# 整条时间线

| 阶段 | 关键动作 | Web 服务器 | Bean 状态 |
|---|---|---|---|
| 构造 `SpringApplication` | 推断 Web 类型、加载 Initializer / Listener | 无 | 无 |
| `prepareEnvironment` | 加载 `application.yml`、绑定 `spring.main.*` | 无 | 无 |
| `createApplicationContext` | 创建空容器 | 无 | 无 |
| `prepareContext` | 设置 Environment、注册主配置类 | 无 | 只有 BeanDefinition |
| `refresh` | 装配、实例化、创建/启动服务器 | 先创建，后启动 | 单例在这里创建 |
| `callRunners` | 执行启动后逻辑 | 已启动 | 已就绪 |
| `started` / `running` | 发布事件 | 已启动 | 已就绪 |

# 常见问题

**为什么 `@PostConstruct` 里访问本机端口会失败？** 因为它在 `finishBeanFactoryInitialization` 阶段执行，此时 Web 服务器已经创建，但 `finishRefresh` 还没调用 `startWebServer()`，端口没有绑定。

**Runner 和 `@PostConstruct` 怎么选？** 只初始化当前 Bean 自己的资源，用 `@PostConstruct`；需要整个容器就绪、要调用本机接口或预热缓存，用 Runner。

**`ContextRefreshedEvent` 和 `ApplicationReadyEvent` 有什么区别？** `ContextRefreshedEvent` 在 `finishRefresh` 里发布，此时 Web 服务器还没启动；`ApplicationReadyEvent` 在所有 Runner 执行完之后发布，才代表应用真正可用。详见 [refresh流程.md](refresh流程.md)。

# 小结

我一向不太喜欢写总结，因为该说的正文里都说了。不过考虑到很多读者是冲着面试来的，还是列成清单：

1. **启动分几步？** 构造 `SpringApplication` → 准备 Environment → 创建 Context → prepareContext → refresh → Runner → started/running。
2. **Web 类型怎么推断？** 有 `DispatcherServlet` + `Servlet` → SERVLET；只有 WebFlux → REACTIVE；否则 NONE。
3. **Environment 为什么先准备？** 创建容器、加载自动配置都要读配置。
4. **prepareContext 和 refresh 的区别？** prepareContext 只注册主配置类，不解析注解；refresh 才真正装配和实例化。
5. **Runner 和 `@PostConstruct` 的区别？** `@PostConstruct` 在 Bean 初始化阶段，服务器还没启动；Runner 在 `refresh()` 之后，服务器已启动。
6. **启动失败怎么处理？** `handleRunFailure` 发布 `ApplicationFailedEvent`、关闭 context、抛出异常。
