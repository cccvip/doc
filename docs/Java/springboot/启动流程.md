Spring Boot 启动的核心不是 Web 服务器，而是 `ApplicationContext`：读配置、创建容器、装配 Bean、执行 Runner。Web 服务器只是 Servlet 应用的一个可选产物——很多 Spring Boot 应用根本不是 Web 应用。

很多人把启动理解成"启动 Tomcat"，其实 Tomcat 只是在 `refresh()` 的一个分支里被创建和启动的。这篇我们把主线放回**容器装配**：Environment → Context → BeanDefinition → Bean 实例化 → Runner。WebServer 只在最后单独说明。

`refresh()` 内部十二步的详细拆解见 [refresh流程.md](refresh流程.md)。

# 先分清几个角色

- **`SpringApplication`**：启动器。负责读配置、创建 `ApplicationContext`、调用 `refresh()`、执行 Runner。它本身不是容器。
- **`ApplicationContext`**：容器。持有 `BeanFactory`、BeanDefinition、单例 Bean、事件发布器。
- **`BeanFactory`**：容器里真正管理 BeanDefinition 和 Bean 实例的部分。
- **`Environment`**：配置环境。`application.yml`、profile、命令行参数、环境变量都合并到这里。

一句话：**`SpringApplication` 负责"启动"，`ApplicationContext` 负责"装东西"。**

# 一、准备 Environment

`run` 的第一件事是准备 Environment，因为后面每一步都要读配置：

```java
private ConfigurableEnvironment prepareEnvironment(SpringApplicationRunListeners listeners,
        ApplicationArguments applicationArguments) {

    ConfigurableEnvironment environment = getOrCreateEnvironment();
    configureEnvironment(environment, applicationArguments.getSourceArgs());
    ConfigurationPropertySources.attach(environment);

    // 发布 environmentPrepared：application.yml 在这一步加载
    listeners.environmentPrepared(environment);

    // 把 spring.main.* 绑定到 SpringApplication
    bindToSpringApplication(environment);

    return environment;
}
```

这里做了四件事：

1. `getOrCreateEnvironment`：按应用类型创建 Environment。Servlet 是 `StandardServletEnvironment`，Reactive 是 `StandardReactiveWebEnvironment`，普通应用是 `StandardEnvironment`。
2. `configureEnvironment`：把命令行参数和 profile 加进去。
3. `listeners.environmentPrepared`：触发 `EnvironmentPostProcessor`，其中最重要的是 `ConfigFileApplicationListener`，负责加载 `application.yml` 和 `application-{profile}.yml`。
4. `bindToSpringApplication`：把 `spring.main.*` 绑定到启动器上，比如 `spring.main.web-application-type`、`spring.main.lazy-initialization`、`spring.main.allow-circular-references`。

**做完之后的状态**：配置全部就绪，但没有任何 Bean。

# 二、创建 ApplicationContext

有了 Environment，接着创建容器：

```java
protected ConfigurableApplicationContext createApplicationContext() {
    return this.applicationContextFactory.create(this.webApplicationType);
}
```

按 `webApplicationType` 创建：

| 类型 | 容器 | 多了什么 |
|---|---|---|
| `SERVLET` | `AnnotationConfigServletWebServerApplicationContext` | 持有内嵌 WebServer、Servlet 作用域 |
| `REACTIVE` | `AnnotationConfigReactiveWebServerApplicationContext` | 响应式 Web 容器 |
| `NONE` | `AnnotationConfigApplicationContext` | 普通容器 |

**此时容器是空的**：没有 BeanDefinition，没有 Bean 实例，也没有 Web 服务器。

顺便说一个细节：注解容器（`GenericApplicationContext`）的 `BeanFactory` 在构造时就已经创建好了，所以 `refresh()` 里的 `obtainFreshBeanFactory` 只是设置序列化 ID；XML 容器才会在这一步重新创建并加载定义。

# 三、prepareContext：只是把主配置类交给容器

容器有了，但还不能 `refresh`，要先把 Environment、初始化器、主配置类交给它：

```java
private void prepareContext(ConfigurableApplicationContext context,
        ConfigurableEnvironment environment, SpringApplicationRunListeners listeners,
        ApplicationArguments applicationArguments) {

    context.setEnvironment(environment);
    applyInitializers(context);
    listeners.contextPrepared(context);
    context.getBeanFactory().registerSingleton("springApplicationArguments", applicationArguments);
    load(context, getAllSources().toArray(new Object[0]));
    listeners.contextLoaded(context);
}
```

这里最关键的是最后一步 `load`：**它只把主配置类 `ApiApplication` 注册成一个 BeanDefinition，并不解析上面的注解。**

`@SpringBootApplication` 里的 `@ComponentScan`、`@EnableAutoConfiguration`，在这一步还没有生效。`applyInitializers` 虽然会执行，但它只能操作 Environment / BeanFactory，不能 `getBean`，因为 Bean 还没创建。

**做完之后的状态**：容器里只有主配置类这一个 BeanDefinition，其他什么都没有。

所以 `prepareContext` 和 `refresh` 的区别是：**prepareContext 只是把"要装配的入口"交给容器；refresh 才真正开始解析注解、创建 Bean。**

# 四、refresh：容器真正开始工作

`refreshContext` 调用 `AbstractApplicationContext.refresh()`。这是容器真正"启动"的地方。完整十二步见 [refresh流程.md](refresh流程.md)，这里抓住和启动器相关的几件事：

**1. BeanDefinition 补齐**

`invokeBeanFactoryPostProcessors` 里的 `ConfigurationClassPostProcessor` 解析 `@Configuration`、`@ComponentScan`、`@Import`，自动装配在这一步发生。到这一步结束，容器里该有的 BeanDefinition 基本都有了。

**2. BeanPostProcessor 注册**

`@Autowired`、AOP 等后置处理器被注册进容器。它们要在 Bean 实例化之前就位，否则注入和代理都赶不上。

**3. Bean 实例化**

`finishBeanFactoryInitialization` 创建所有非懒加载的单例。`@PostConstruct`、`InitializingBean.afterPropertiesSet()`、`init-method` 都在这一步执行；AOP 代理在 `postProcessAfterInitialization` 里生成。

**4. 容器就绪事件**

`finishRefresh` 发布 `ContextRefreshedEvent`，表示容器刷新完成。注意：**此时 Web 服务器还没有启动**。

**5. Web 服务器（仅 Servlet 应用）**

`onRefresh` 创建 WebServer，`finishRefresh` 启动它。这是 Servlet 应用的分支，不是启动的主线。具体时序见 [refresh流程.md](refresh流程.md)。

所以 refresh 结束时，**与启动器相关的核心产出**是：

- BeanDefinition 齐全；
- 单例 Bean 创建完成，AOP 代理已生成；
- 容器刷新完成事件已发布。

# 五、Runner

`refresh()` 结束后，`run` 还会执行 Runner：

```java
private void callRunners(ApplicationContext context, ApplicationArguments args) {
    List<Object> runners = new ArrayList<>();
    runners.addAll(context.getBeansOfType(ApplicationRunner.class).values());
    runners.addAll(context.getBeansOfType(CommandLineRunner.class).values());
    AnnotationAwareOrderComparator.sort(runners);

    for (Object runner : new LinkedHashSet<>(runners)) {
        if (runner instanceof ApplicationRunner) {
            callRunner((ApplicationRunner) runner, args);
        }
        if (runner instanceof CommandLineRunner) {
            callRunner((CommandLineRunner) runner, args);
        }
    }
}
```

`ApplicationRunner` 和 `CommandLineRunner` 都在 **refresh 完成、Web 服务器启动之后**执行。适合做缓存预热、调用本机接口、初始化业务数据。

**和 `@PostConstruct` 的区别**：

| 方式 | 执行时机 | Web 服务器 |
|---|---|---|
| `@PostConstruct` | Bean 初始化阶段 | 已创建，未启动 |
| `ContextRefreshedEvent` | `finishRefresh` 的父类部分 | 未启动 |
| `ApplicationRunner` | refresh 之后 | 已启动 |

所以如果要在启动后调用本服务 HTTP 接口，应该用 Runner，不要用 `@PostConstruct` 或 `ContextRefreshedEvent`。

多个 Runner 之间用 `@Order` / `Ordered` 排序。Runner 里抛异常会走 `handleRunFailure`，整个应用启动失败。

# 六、started / running

最后，`run` 会通知监听器：

```java
listeners.started(context);   // refresh 完成、Runner 执行前
// ...
listeners.running(context);   // Runner 执行完、应用就绪
```

对应的事件：

- `ApplicationStartedEvent`：`refresh()` 完成、Runner 执行前；
- `ApplicationReadyEvent`：Runner 执行完、应用正式 ready。

如果中间任何一步抛异常，会走 `handleRunFailure`：发布 `ApplicationFailedEvent`、关闭已经创建的 context、把异常抛出去。

# 整条时间线

| 阶段 | 关键动作 | Bean 状态 |
|---|---|---|
| 构造 `SpringApplication` | 推断 Web 类型、加载 Initializer / Listener | 无 |
| `prepareEnvironment` | 加载 `application.yml`、绑定 `spring.main.*` | 无 |
| `createApplicationContext` | 创建空容器 | 无 |
| `prepareContext` | 设置 Environment、注册主配置类 | 只有 BeanDefinition |
| `refresh` | 装配、实例化、发布容器刷新事件 | 单例在这里创建 |
| `callRunners` | 执行启动后逻辑 | 已就绪 |
| `started` / `running` | 发布事件 | 已就绪 |

# 常见误解

1. **`prepareContext` 会解析 `@SpringBootApplication`**：不会，它只注册 BeanDefinition，注解要等 `refresh()` 才解析。
2. **Spring Boot 启动就是启动 Tomcat**：Tomcat 只是 Servlet 应用在 `refresh()` 里的一个分支，不是主线。
3. **`ContextRefreshedEvent` 代表服务可用**：不代表，此时 Web 服务器还没启动；`ApplicationReadyEvent` 才是。
4. **`@PostConstruct` 里能访问本机端口**：不能，Web 服务器还没 `start()`。
5. **`refresh()` 可以调多次**：`GenericApplicationContext` 第二次调用直接抛异常。
6. **Runner 里抛异常只是日志警告**：不是，会触发 `handleRunFailure`，启动失败。

# 小结

我一向不太喜欢写总结，因为该说的正文里都说了。不过考虑到很多读者是冲着面试来的，还是列成清单：

1. **启动分几步？** 构造 `SpringApplication` → 准备 Environment → 创建 Context → prepareContext → refresh → Runner → started/running。
2. **Environment 为什么先准备？** 创建容器、加载自动配置都要读配置。
3. **prepareContext 和 refresh 的区别？** prepareContext 只注册主配置类，不解析注解；refresh 才真正装配和实例化。
4. **Spring Boot 启动的核心是什么？** `ApplicationContext` 的装配，不是 Web 服务器。
5. **Runner 和 `@PostConstruct` 的区别？** `@PostConstruct` 在 Bean 初始化阶段，服务器还没启动；Runner 在 `refresh()` 之后，服务器已启动。
6. **启动失败怎么处理？** `handleRunFailure` 发布 `ApplicationFailedEvent`、关闭 context、抛出异常。
