把 Spring Boot 启动说成"创建容器、启动 Tomcat"都不准确。Boot 真正做的是：**按注解的指示，把应用组装起来**。`SpringApplication.run` 只是个触发器，真正决定"装什么、不装什么"的，是 `@SpringBootApplication` 这一组注解。

这篇以注解为主线：先给一条流程骨架定位，再把 `@SpringBootApplication` 拆开，讲清自动配置从哪来、条件怎么过滤、组件怎么扫描、配置怎么绑定。

# 一句话流程骨架

```text
main
 └─ SpringApplication.run
     ├─ 准备 Environment          （读 application.yml、profile、命令行参数）
     ├─ 创建 ApplicationContext
     ├─ prepareContext            （把主配置类注册成 BeanDefinition）
     ├─ refresh
     │   └─ invokeBeanFactoryPostProcessors
     │        └─ ConfigurationClassPostProcessor
     │             └─ 解析 @SpringBootApplication 及其派生的所有注解
     └─ 执行 Runner
```

关键在最后一步：**所有注解都在 `refresh()` 的 `ConfigurationClassPostProcessor` 里被解析**，`@ComponentScan`、`@Import`、自动配置全部在这里落地。`prepareContext` 只是把主配置类登记成 BeanDefinition，注解还没解析。

流程的详细拆解见 [refresh流程.md](refresh流程.md)，这篇不重复。

# @SpringBootApplication 不是一个注解

```java
@SpringBootApplication
public class ApiApplication {
    public static void main(String[] args) {
        SpringApplication.run(ApiApplication.class, args);
    }
}
```

它等价于三个注解的组合：

```java
@SpringBootConfiguration
@EnableAutoConfiguration
@ComponentScan
public class ApiApplication { ... }
```

三个注解各管一摊：

| 注解 | 职责 |
|---|---|
| `@SpringBootConfiguration` | 把自己标记成配置类 |
| `@EnableAutoConfiguration` | 加载第三方 jar 里的自动配置 |
| `@ComponentScan` | 扫描用户自己写的 Bean |

下面逐个拆。

# 一、@SpringBootConfiguration：本质是 @Configuration

```java
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@Configuration
@Indexed
public @interface SpringBootConfiguration { }
```

它自己没什么逻辑，就是 `@Configuration` 加了个 `@Indexed`（用于加快扫描）。所以理解 `@SpringBootConfiguration` 就是理解 `@Configuration`：

- `@Configuration` 标记的类里，`@Bean` 方法会被注册成 BeanDefinition；
- 当 `proxyBeanMethods = true`（默认）时，Spring 会用 CGLIB 生成子类，保证 `@Bean` 方法之间互相调用返回的是同一个单例；
- 如果 `@Bean` 方法之间不互相调用，`proxyBeanMethods = false` 可以省掉代理，Boot 自己的配置类基本都用这个。

**为什么叫 `SpringBootConfiguration` 而不是直接用 `@Configuration`？** 一是语义上声明"这是 Boot 应用的主配置类"，二是给 Boot 一个可识别的标记——`@SpringBootTest` 找主配置类时就靠它。一个应用只应该有一个。

# 二、@EnableAutoConfiguration：自动配置从哪来

```java
@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
@Inherited
@AutoConfigurationPackage
@Import(AutoConfigurationImportSelector.class)
public @interface EnableAutoConfiguration {
    Class<?>[] exclude() default {};
    String[] excludeName() default {};
}
```

它由两部分组成：`@AutoConfigurationPackage` 和 `@Import(AutoConfigurationImportSelector.class)`。

## 2.1 @AutoConfigurationPackage：记录启动类所在包

```java
@Import(AutoConfigurationPackages.Registrar.class)
public @interface AutoConfigurationPackage { }
```

`Registrar` 做的事很简单：把启动类 `ApiApplication` 所在的**包名**注册进容器，作为一个可查询的"自动配置包"。

**有什么用？** 后续很多框架要"从某个包开始扫"——JPA 扫 `@Entity`、MyBatis 扫 `@Mapper`、Spring Data 扫 Repository——它们默认就用这个包。所以**启动类放在哪个包，决定了这些框架的默认扫描范围**，这也是为什么启动类要放在最外层包。

## 2.2 @Import(AutoConfigurationImportSelector)：真正干活的人

`AutoConfigurationImportSelector` 负责"挑出要加载哪些自动配置类"。核心方法：

```java
protected AutoConfigurationEntry getAutoConfigurationEntry(AnnotationMetadata annotationMetadata) {
    if (!isEnabled(annotationMetadata)) {
        return EMPTY_ENTRY;
    }
    AnnotationAttributes attributes = getAttributes(annotationMetadata);

    // ① 拿到所有候选自动配置类
    List<String> configurations = getCandidateConfigurations(annotationMetadata, attributes);

    // ② 去重
    configurations = removeDuplicates(configurations);

    // ③ 排除
    Set<String> exclusions = getExclusions(annotationMetadata, attributes);
    checkExcludedClasses(configurations, exclusions);
    configurations.removeAll(exclusions);

    // ④ 提前过滤（OnClassCondition 等）
    configurations = getConfigurationClassFilter().filter(configurations);

    // ⑤ 发事件
    fireAutoConfigurationImportEvents(configurations, exclusions);
    return new AutoConfigurationEntry(configurations, exclusions);
}
```

**候选清单从哪读？**

```java
protected List<String> getCandidateConfigurations(AnnotationMetadata metadata, AnnotationAttributes attributes) {
    List<String> configurations = SpringFactoriesLoader.loadFactoryNames(
            getSpringFactoriesLoaderFactoryClass(), getBeanClassLoader());
    // ...
    return configurations;
}
```

- **2.7 以前**：`SpringFactoriesLoader.loadFactoryNames(EnableAutoConfiguration.class, ...)`，读所有 jar 里 `META-INF/spring.factories` 中 key 为 `org.springframework.boot.autoconfigure.EnableAutoConfiguration` 的类名列表。
- **2.7 起**：改读 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`，一行一个类名。

**关键认知**：候选清单来自**第三方 jar**，不是你项目里写的。Spring 自己的 `spring-boot-autoconfigure` 提供了一份，各 starter 也可能追加。

**排除怎么做？** 三个途径：

- `@SpringBootApplication(exclude = XxxAutoConfiguration.class)`；
- `@SpringBootApplication(excludeName = "com.xxx.XxxAutoConfiguration")`；
- 配置 `spring.autoconfigure.exclude=...`。

# 三、条件注解：不是"全装"，是"按条件装"

`getCandidateConfigurations` 读出来的候选有上百个（2.5.x 约 130+），但不会全部生效。每个自动配置类上都挂着条件注解，不满足就不装。

常见条件注解：

| 注解 | 生效条件 |
|---|---|
| `@ConditionalOnClass` | classpath 上存在指定类 |
| `@ConditionalOnMissingClass` | classpath 上不存在指定类 |
| `@ConditionalOnBean` | 容器里已存在指定 Bean |
| `@ConditionalOnMissingBean` | 容器里不存在指定 Bean |
| `@ConditionalOnProperty` | 指定配置等于某值 |
| `@ConditionalOnWebApplication` | 当前是 Web 应用 |
| `@ConditionalOnResource` | 存在指定资源文件 |
| `@ConditionalOnExpression` | SpEL 表达式为 true |

以 `DataSourceAutoConfiguration` 为例：

```java
@Configuration(proxyBeanMethods = false)
@ConditionalOnClass({ DataSource.class, EmbeddedDatabaseType.class })   // 有 jdbc 依赖才装
@EnableConfigurationProperties(DataSourceProperties.class)
@Import({ DataSourcePoolMetadataProvidersConfiguration.class, ... })
public class DataSourceAutoConfiguration {

    @Configuration(proxyBeanMethods = false)
    @Conditional(PooledDataSourceCondition.class)
    @ConditionalOnMissingBean({ DataSource.class, XADataSource.class })  // 用户没自定义才装
    @Import({ DataSourceConfiguration.Hikari.class, ... })
    protected static class PooledDataSourceConfiguration { }
}
```

这两行条件解释了两个常见现象：

- **为什么没引 `spring-boot-starter-jdbc` 就不会创建 `DataSource`？** 因为 `@ConditionalOnClass(DataSource.class)` 不满足；
- **为什么自己定义了一个 `DataSource` Bean，自动配置就不生效了？** 因为 `@ConditionalOnMissingBean(DataSource.class)` 不满足——**用户自定义优先**是 Boot 自动配置的核心约定。

这些注解最终都指向 `@Conditional`，由对应的 `Condition.matches()` 决定结果，比如 `OnClassCondition` 处理 `@ConditionalOnClass`、`OnBeanCondition` 处理 `@ConditionalOnMissingBean`。

# 四、@ComponentScan：扫用户自己的 Bean

```java
@ComponentScan(excludeFilters = {
        @Filter(type = FilterType.CUSTOM, classes = TypeExcludeFilter.class),
        @Filter(type = FilterType.CUSTOM, classes = AutoConfigurationExcludeFilter.class) })
```

它负责把你写的 Bean 扫进容器：

- **默认 base package** = 启动类所在包，及其子包（这也是启动类要放最外层的另一个原因）；
- 识别 `@Component` 及其派生：`@Service`、`@Repository`、`@Controller`、`@RestController`、`@Configuration`；
- 可以用 `@SpringBootApplication(scanBasePackages = ...)` 改扫描范围。

注意 `@SpringBootApplication` 自带的两个排除过滤器：

- `TypeExcludeFilter`：给用户自定义排除用的扩展点；
- `AutoConfigurationExcludeFilter`：**把自动配置类从扫描里排除**，避免它们同时被 `@Import` 和 `@ComponentScan` 注册两次。

**和 `@EnableAutoConfiguration` 的分工**：

| | 扫什么 | Bean 从哪来 |
|---|---|---|
| `@ComponentScan` | 你写的类 | 你的项目 |
| `@EnableAutoConfiguration` | 自动配置类 | 第三方 jar |

# 五、@ConfigurationProperties：配置怎么绑到 POJO

自动配置类本身也要读配置。这时用：

```java
@EnableConfigurationProperties(DataSourceProperties.class)
```

它把 `DataSourceProperties` 注册成 Bean，并按 `@ConfigurationProperties(prefix = "spring.datasource")` 把 `application.yml` 里的 `spring.datasource.*` 绑定上去。

- `@ConfigurationProperties(prefix = "xxx")`：声明前缀，支持松散绑定（`data-source` / `dataSource` / `DATA_SOURCE` 都能匹配）；
- `@EnableConfigurationProperties(Xxx.class)`：主动注册并绑定；
- `@ConfigurationPropertiesScan`：2.2+ 可以直接扫包下的 `@ConfigurationProperties` 类。

这样自动配置类就能像下面这样用配置：

```java
@Bean
@ConditionalOnMissingBean
public DataSource dataSource(DataSourceProperties properties) {
    return properties.initializeDataSourceBuilder().build();
}
```

# 把这些放回流程

再回到开头的骨架，把注解挂上去：

```text
SpringApplication.run
 ├─ prepareContext
 │   └─ 主配置类注册为 BeanDefinition（此时注解还没解析）
 └─ refresh
     └─ invokeBeanFactoryPostProcessors
         └─ ConfigurationClassPostProcessor
             ├─ 解析 @Configuration / @SpringBootConfiguration
             ├─ 解析 @ComponentScan → 注册用户 Bean
             ├─ 解析 @Import
             │   └─ AutoConfigurationImportSelector
             │       ├─ 读 spring.factories / AutoConfiguration.imports
             │       ├─ 去重、排除
             │       └─ 条件过滤 → 注册自动配置类
             └─ 解析 @Bean → 注册 BeanDefinition
     └─ finishBeanFactoryInitialization → 实例化 Bean
```

所以：**注解定义了"装配的指令"，`refresh()` 里的 `ConfigurationClassPostProcessor` 执行这些指令。** 两者是"声明"和"执行"的关系。

# 常见误解

1. **`@SpringBootApplication` 是一个注解**：不是，它是 `@SpringBootConfiguration` + `@EnableAutoConfiguration` + `@ComponentScan` 的组合。
2. **自动配置"全都装配"**：不是，候选有上百个，最终装哪些由条件注解决定。
3. **自动配置类在你项目里**：不在，来自第三方 jar 的 `spring.factories`（2.7 前）或 `AutoConfiguration.imports`（2.7+）。
4. **2.7 之后还用 `spring.factories` 加载自动配置**：自动配置已迁到 `AutoConfiguration.imports`；`spring.factories` 仍用于 `ApplicationContextInitializer` 等其他扩展点。
5. **`@ComponentScan` 和 `@EnableAutoConfiguration` 是一回事**：不是，一个扫你写的 Bean，一个加载第三方配置。
6. **启动类放哪个包无所谓**：有所谓，它决定 `@ComponentScan` 的默认范围和 `@AutoConfigurationPackage` 记录的包。
7. **去掉 `@EnableAutoConfiguration` 也能正常跑**：能启动，但没有任何自动配置——数据源、MVC、Redis 都不会装。

# 小结

我一向不太喜欢写总结，因为该说的正文里都说了。不过考虑到很多读者是冲着面试来的，还是列成清单：

1. **`@SpringBootApplication` 由什么组成？** `@SpringBootConfiguration` + `@EnableAutoConfiguration` + `@ComponentScan`。
2. **`@EnableAutoConfiguration` 由什么组成？** `@AutoConfigurationPackage` + `@Import(AutoConfigurationImportSelector)`。
3. **自动配置候选从哪来？** 第三方 jar 的 `spring.factories`（2.7 前）/ `AutoConfiguration.imports`（2.7+）。
4. **自动配置怎么决定装不装？** 条件注解：`@ConditionalOnClass`、`@ConditionalOnMissingBean` 等。
5. **为什么自定义 Bean 能覆盖自动配置？** `@ConditionalOnMissingBean` 让自动配置在用户已定义时退让。
6. **`@ComponentScan` 扫什么？** 扫你写的 `@Component` 及派生类，默认从启动类所在包开始。
7. **这些注解什么时候生效？** `refresh()` 的 `invokeBeanFactoryPostProcessors` → `ConfigurationClassPostProcessor`。
