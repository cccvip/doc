面试聊 Spring Boot 启动，如果开口就是"创建容器、扫描 Bean、启动 Tomcat"，基本就到头了。这三个词谁都会背，可一旦被追问"谁在做这些事、依据什么做、为什么是这个顺序"，就答不上来。

Spring Boot 的启动其实是两层。外层是 `SpringApplication`，负责把配置读进来、把容器建出来、在合适的时机触发容器的刷新。内层是容器的 `refresh`，应用的装配和 Bean 的创建都发生在那里。`@SpringBootApplication` 这类注解本身不"执行"任何东西，它们是一份装配说明，等 `refresh` 走到某一步时才被读取。

把这条线捋顺，面试常问的几个点就都能挂上去。所以下面先给骨架，再挑几个真正有区分度的点展开，源码不贴——成熟框架要看的是全局和关键节点，不是逐行翻译。

## 先看骨架

一次启动大致走这么几步：

```
准备配置(Environment)
  → 创建空容器(ApplicationContext)
  → 把主配置类登记进容器
  → refresh：解析注解、创建 Bean
  → 执行 Runner
```

前面三步很轻。读 `application.yml`、合并 profile 和命令行参数，装进 `Environment`；然后按应用类型建一个 `ApplicationContext`，这会儿它还是个空壳；再把启动类注册成一个 BeanDefinition。到这三步结束，容器里一个业务 Bean 都没有。

真正干活的是第四步 `refresh`。`@ComponentScan` 扫出来的类、自动配置导进来的类、`@Bean` 方法声明的 Bean，全在这一步变成 BeanDefinition，紧接着被实例化成对象。Runner 是最后收尾，跑一些"启动之后才做"的逻辑。

骨架本身不难，面试的区分度在边界。启动类在第三步只是被登记，注解一个都还没解析；Web 服务器直到第四步才创建。边界说不清，细节一问就露馅。

## 面试点一：@SpringBootApplication 到底是什么

它不是一个注解，是三个拼起来的：`@SpringBootConfiguration`、`@EnableAutoConfiguration`、`@ComponentScan`。

三个各管一摊。`@SpringBootConfiguration` 本质就是 `@Configuration`，只多了一层语义，标明"这是主配置类"，`@SpringBootTest` 找的就是它。`@ComponentScan` 负责扫你自己写的 Bean。`@EnableAutoConfiguration` 负责把第三方 jar 里的自动配置装配进来。

能脱口说出"它是组合注解、由哪三个组成、分别干什么"，和只会说"它是启动注解"，是两个层次。

## 面试点二：自动配置从哪来

`@EnableAutoConfiguration` 内部由两部分组成：`@AutoConfigurationPackage` 和 `@Import(AutoConfigurationImportSelector.class)`。

`@AutoConfigurationPackage` 做一件小事：把启动类所在的包名记下来。后面 JPA 扫实体、MyBatis 扫 Mapper，默认就用这个包。启动类要放最外层包，这也是原因之一。

挑自动配置的是 `AutoConfigurationImportSelector`。它先读候选清单——2.7 之前读各 jar 里的 `META-INF/spring.factories`，2.7 起改读 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`。清单来自第三方 jar，不是你项目里写的，这是很多人第一次听会愣一下的点。读出来之后，去重、排除（`@SpringBootApplication(exclude = ...)` 和 `spring.autoconfigure.exclude` 都在这里生效），再交给条件过滤。

面试很爱追问一句："我没引 Redis 依赖，为什么就没有 RedisTemplate？"答案就埋在这段里——候选虽然被读出来了，但没通过后面的条件判断。

## 面试点三：条件注解与 @ConditionalOnMissingBean

候选清单上百个自动配置类，真正生效的只是一部分。每个自动配置类上都挂着条件注解，满足才装配。

高频的几个：`@ConditionalOnClass`（classpath 上有这个类才装）、`@ConditionalOnMissingBean`（容器里没有这个 Bean 才装）、`@ConditionalOnProperty`（某个配置等于某值才装）、`@ConditionalOnWebApplication`（是 Web 应用才装）。

拿数据源说。`DataSourceAutoConfiguration` 的条件是"classpath 上有 `DataSource`"，所以不引 JDBC 依赖就不会有数据源；它内部又有 `@ConditionalOnMissingBean`，所以你自己定义了一个 `DataSource`，自动配置主动退让。**用户自定义优先**是整套自动配置的约定，也是面试最想听的那句话。

## 面试点四：@ComponentScan 的扫描范围

默认扫启动类所在包及其子包。启动类放错位置——比如塞进某个子包里——上层包写的 Bean 就扫不到，这是新手最常踩的坑之一。

还要分清两件事：`@ComponentScan` 扫的是你项目里的类，`@EnableAutoConfiguration` 装的是第三方 jar 里的配置，职责不同。`@SpringBootApplication` 里额外挂了两个排除过滤器，其中一个专门把自动配置类从扫描范围里剔掉，避免同一个配置既被扫描、又被导入，注册两遍。

## 把注解挂回启动流程

这几个注解都在 `refresh` 的 `invokeBeanFactoryPostProcessors` 阶段、由 `ConfigurationClassPostProcessor` 解析。在此之前，它们只是挂在主配置类旁边的一堆标记。

顺着这条线，有两个顺序问题面试几乎必问。

`@PostConstruct` 在 Bean 实例化阶段执行，那时 Web 服务器已经创建但还没启动，所以在里面访问本机端口会失败。

`ContextRefreshedEvent` 发布的时候，Web 服务器其实已经启动了——2.5 里是 `WebServerStartStopLifecycle` 在 `refresh` 收尾时先起的服务，事件随后发出。真正代表"应用完全可用"的是 `ApplicationReadyEvent`，它在 Runner 跑完之后才发。

## 面试速记

- `@SpringBootApplication` = `@SpringBootConfiguration` + `@EnableAutoConfiguration` + `@ComponentScan`。
- `@EnableAutoConfiguration` = `@AutoConfigurationPackage` + `@Import(AutoConfigurationImportSelector)`。
- 自动配置候选来自第三方 jar：2.7 前是 `spring.factories`，之后是 `AutoConfiguration.imports`。
- 装不装由条件注解决定，`@ConditionalOnMissingBean` 让自定义 Bean 覆盖自动配置。
- `@ComponentScan` 从启动类所在包往下扫，所以启动类要放最外层。
- 注解在 `refresh` 的 `ConfigurationClassPostProcessor` 里解析，`prepareContext` 阶段还没轮到它们。
- `@PostConstruct` 时服务器没启动；`ApplicationReadyEvent` 时应用才可用。
