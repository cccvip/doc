我们平时写 Spring Boot，启动就是一行 `SpringApplication.run(ApiApplication.class, args)`。但这一行里到底发生了什么，很多人只有一个模糊印象：创建容器、扫描 Bean、启动 Tomcat。真到面试被问"Web 服务器是在哪一步起来的、`@PostConstruct` 和 Runner 谁先执行"，就容易卡住。

这篇我们跟着 `SpringApplication.run` 的源码走一遍，把每一步在做什么、为什么放在这个位置、做完之后容器变成什么样讲清楚。源码只保留关键行，省略的部分会标出来。

> 基于 Spring Boot 2.5.x。Boot 3 把 `javax.servlet` 换成了 `jakarta.servlet`，主流程不变。

# 先分清两个东西：SpringApplication 和 ApplicationContext

看启动流程之前，先把这几个角色分清楚，不然后面很容易混：

- **`SpringApplication`**：启动器。它负责读配置、创建 `ApplicationContext`、调用 `refresh()`、执行 Runner。它本身不是容器，也不持有业务 Bean。
- **`ApplicationContext`**：容器。它持有 `BeanFactory`、BeanDefinition、单例 Bean、事件发布器、资源加载器。我们平时说的"Spring 容器"，通常指它。
- **`BeanFactory`**：最底层的 Bean 容器，负责 `getBean`、创建 Bean。`ApplicationContext` 是在它外面加了一层：事件、国际化、资源加载、环境。
- **`Environment`**：配置环境。`application.yml`、profile、命令行参数、环境变量，最终都合并到这里。

记住一句话：**`SpringApplication` 是"启动器"，`ApplicationContext` 是"容器"，`BeanFactory` 是"容器里真正管 Bean 的那部分"。**

# 从 main 方法开始

```java
@SpringBootApplication
public class ApiApplication {
    public static void main(String[] args) {
        SpringApplication.run(ApiApplication.class, args);
    }
}
```

`SpringApplication.run` 先创建一个 `SpringApplication`，再调用实例的 `run`：

```java
public static ConfigurableApplicationContext run(Class<?> primarySource, String... args) {
    return new SpringApplication(primarySource).run(args);
}
```

构造方法里做了三件事，每一件都会影响后面的流程：

```java
public SpringApplication(ResourceLoader resourceLoader, Class<?>... primarySources) {
    this.primarySources = new LinkedHashSet<>(Arrays.asList(primarySources));

    // ① 根据 classpath 推断应用类型：SERVLET / REACTIVE / NONE
    this.webApplicationType = WebApplicationType.deduceFromClasspath();

    // ② 从 spring.factories 加载初始化器和监听器
    setInitializers((Collection) getSpringFactoriesInstances(ApplicationContextInitializer.class));
    setListeners((Collection) getSpringFactoriesInstances(ApplicationListener.class));

    // ③ 推断 main 方法所在类
    this.mainApplicationClass = deduceMainApplicationClass();
}
```

**第一件事：推断 Web 类型。** `WebApplicationType.deduceFromClasspath()` 看 classpath 上有没有特定的类：

- 有 `DispatcherServlet` 和 `Servlet` → `SERVLET`；
- 没有 Servlet、但有 WebFlux 的 `DispatcherHandler` → `REACTIVE`；
- 都没有 → `NONE`。

这个类型决定了后面创建哪种 `ApplicationContext`，也决定了要不要启动内嵌 Web 服务器。

**第二件事：加载 Initializer 和 Listener。** 它们是从 `META-INF/spring.factories` 里读出来的扩展点：

- `ApplicationContextInitializer`：在 `refresh()` 之前对容器做编程式定制，比如注册 `BeanFactoryPostProcessor`、设置 profile；
- `ApplicationListener`：监听启动过程中的事件，比如 `ApplicationReadyEvent`。

**第三件事：推断主类。** 从当前线程的调用栈里找到 `main` 方法所在的类，主要用于日志和异常提示。

构造完成后，`SpringApplication` 手里有了：应用类型、初始化器、监听器、主类。接下来进入实例的 `run`。

# 第一步：准备 Environment

`run` 里的第一件正事是准备 `Environment`。为什么不是先创建容器？因为创建哪种容器、加载哪些自动配置、连不连数据库，都要先读配置。

```java
private ConfigurableEnvironment prepareEnvironment(SpringApplicationRunListeners listeners,
        ApplicationArguments applicationArguments) {

    // ① 创建 Environment
    ConfigurableEnvironment environment = getOrCreateEnvironment();

    // ② 把命令行参数、profile 等加进去
    configureEnvironment(environment, applicationArguments.getSourceArgs());
    ConfigurationPropertySources.attach(environment);

    // ③ 发布 environmentPrepared 事件：application.yml 在这一步加载
    listeners.environmentPrepared(environment);

    // ④ 把 spring.main.* 绑定到 SpringApplication
    bindToSpringApplication(environment);

    return environment;
}
```

`getOrCreateEnvironment()` 会按 Web 类型创建不同的 Environment：Servlet 应用是 `StandardServletEnvironment`，Reactive 是 `StandardReactiveWebEnvironment`，普通应用是 `StandardEnvironment`。

`configureEnvironment` 做两件事：把命令行参数包装成 `PropertySource` 加进去；把 profile 激活。注意，这时 `application.yml` 还没加载。

`listeners.environmentPrepared(environment)` 会触发 `EnvironmentPostProcessor`，其中最重要的是 `ConfigFileApplicationListener`：它负责找 `application.yml` / `application.properties`，按 profile 加载，并合并到 Environment 里。

`bindToSpringApplication` 会把 `spring.main.*` 这一组配置绑定到 `SpringApplication` 上，比如：

- `spring.main.web-application-type`：手动指定 Web 类型；
- `spring.main.lazy-initialization`：是否延迟初始化 Bean；
- `spring.main.allow-circular-references`：是否允许循环依赖；
- `spring.main.banner-mode`：Banner 的显示方式。

**做完之后的状态**：Environment 里已经有了所有配置，但还没有任何 Bean。下一步创建容器时，会用这个 Environment 决定行为。

# 第二步：创建 ApplicationContext

有了 Environment，接着创建容器：

```java
protected ConfigurableApplicationContext createApplicationContext() {
    return this.applicationContextFactory.create(this.webApplicationType);
}
```

`ApplicationContextFactory` 根据 `webApplicationType` 创建对应的容器：

| 类型 | 容器 | 特点 |
|---|---|---|
| `SERVLET` | `AnnotationConfigServletWebServerApplicationContext` | 持有内嵌 Web 服务器 |
| `REACTIVE` | `AnnotationConfigReactiveWebServerApplicationContext` | 响应式 Web 容器 |
| `NONE` | `AnnotationConfigApplicationContext` | 普通容器 |

以 Servlet 为例，`AnnotationConfigServletWebServerApplicationContext` 继承链里有两个关键能力：

- `ServletWebServerApplicationContext`：持有 `WebServer` 字段，负责创建和启动内嵌服务器；
- `AnnotationConfigRegistry`：支持 `register(Class<?>...)` 注册注解配置类。

**做完之后的状态**：容器对象有了，但它是**空的**——没有 BeanDefinition，没有 Bean 实例，也没有 Web 服务器。真正的装配要等 `refresh()`。

# 第三步：prepareContext

容器创建出来后，不能直接 `refresh`，要先把 Environment、初始化器、主配置类交给它：

```java
private void prepareContext(ConfigurableApplicationContext context,
        ConfigurableEnvironment environment, SpringApplicationRunListeners listeners,
        ApplicationArguments applicationArguments) {

    // ① 设置 Environment
    context.setEnvironment(environment);

    // ② 应用初始化器：refresh 之前对容器做定制
    applyInitializers(context);

    // ③ 发布 contextPrepared 事件
    listeners.contextPrepared(context);

    // ④ 注册启动参数，让 Bean 可以注入 ApplicationArguments
    context.getBeanFactory().registerSingleton("springApplicationArguments", applicationArguments);

    // ⑤ 把主配置类（ApiApplication）注册进容器
    load(context, getAllSources().toArray(new Object[0]));

    // ⑥ 发布 contextLoaded 事件
    listeners.contextLoaded(context);
}
```

`applyInitializers` 会遍历前面加载的 `ApplicationContextInitializer`，逐个调用 `initialize(context)`。这个时机很关键：容器已经有了，但还没 `refresh`，所以初始化器可以往容器里加 `BeanFactoryPostProcessor`、设置 profile、注册自定义作用域，但不能 `getBean`。

`load(context, sources)` 会把主配置类 `ApiApplication` 注册成一个 BeanDefinition。注意：**只是注册了定义，还没有解析它上面的注解**。`@SpringBootApplication` 里的 `@ComponentScan`、`@EnableAutoConfiguration`，要等到 `refresh()` 阶段才处理。

**做完之后的状态**：容器里只有主配置类这一个 BeanDefinition，其他什么都没有。

# 第四步：refresh

`refreshContext` 会调用 `AbstractApplicationContext.refresh()`。这是整个启动流程最核心的一步，我们拆开看。

## refresh 的全貌

```java
public void refresh() throws BeansException, IllegalStateException {
    prepareRefresh();

    // ① 创建 / 获取 BeanFactory
    ConfigurableListableBeanFactory beanFactory = obtainFreshBeanFactory();
    prepareBeanFactory(beanFactory);

    try {
        postProcessBeanFactory(beanFactory);

        // ② 执行 BeanFactoryPostProcessor：自动装配在这里
        invokeBeanFactoryPostProcessors(beanFactory);

        // ③ 注册 BeanPostProcessor
        registerBeanPostProcessors(beanFactory);

        initMessageSource();
        initApplicationEventMulticaster();

        // ④ 创建内嵌 Web 服务器（还没启动）
        onRefresh();

        registerListeners();

        // ⑤ 实例化所有非懒加载单例
        finishBeanFactoryInitialization(beanFactory);

        // ⑥ 启动 Web 服务器
        finishRefresh();
    }
    catch (BeansException ex) {
        destroyBeans();
        cancelRefresh(ex);
        throw ex;
    }
}
```

下面逐段解释。

## 1. prepareRefresh / obtainFreshBeanFactory / prepareBeanFactory

`prepareRefresh` 做启动前的准备：记录启动时间、设置 `active` 标志、初始化 `PropertySource`、检查必需属性。

`obtainFreshBeanFactory` 负责拿到 `BeanFactory`。这里有一个容易忽略的差异：

- 对 `AnnotationConfigApplicationContext` 这种 `GenericApplicationContext`，`BeanFactory` 在构造时就已经创建好了，`refreshBeanFactory` 只是设置序列化 ID；
- 对 XML 的 `AbstractRefreshableApplicationContext`，这一步会**新建** `DefaultListableBeanFactory` 并加载 XML 里的 BeanDefinition。

`prepareBeanFactory` 会往容器里注册一批"基础设施"：

- `environment`、`systemProperties`、`systemEnvironment` 三个单例；
- `ApplicationContextAwareProcessor`：处理 `ApplicationContextAware`、`EnvironmentAware` 等回调；
- `ApplicationListenerDetector`：识别 `ApplicationListener`；
- 把 `BeanFactory`、`ResourceLoader`、`ApplicationEventPublisher`、`ApplicationContext` 注册成"可解析依赖"，这样 Bean 可以直接注入它们；
- 如果需要，注册 `LoadTimeWeaverAwareProcessor`。

这一步的目的很直接：**让后面的 Bean 能注入容器本身**，而不需要用户自己定义这些 Bean。

## 2. invokeBeanFactoryPostProcessors：自动装配发生在这里

`invokeBeanFactoryPostProcessors` 会执行所有 `BeanFactoryPostProcessor`。这里有两个阶段：

1. 先执行 `BeanDefinitionRegistryPostProcessor`，它可以在普通 Bean 实例化之前注册新的 BeanDefinition；
2. 再执行普通的 `BeanFactoryPostProcessor`，它只能修改已有的 BeanDefinition。

自动装配的核心 `ConfigurationClassPostProcessor` 就是一个 `BeanDefinitionRegistryPostProcessor`。它会：

- 找出所有候选配置类（`@Configuration`、`@Component`、`@Import` 等）；
- 解析 `@ComponentScan`，扫描出更多 BeanDefinition；
- 解析 `@Import`，其中就包括 `@EnableAutoConfiguration` 引入的 `AutoConfigurationImportSelector`；
- 解析 `@Bean` 方法，注册对应的 BeanDefinition。

所以到这一步结束，**容器里该有的 BeanDefinition 基本都有了**，但还没有 Bean 实例。自动配置的细节见 [starter.md](starter.md)。

## 3. registerBeanPostProcessors

BeanDefinition 有了，但创建 Bean 还需要 `BeanPostProcessor`，比如：

- `AutowiredAnnotationBeanPostProcessor`：处理 `@Autowired`；
- `AnnotationAwareAspectJAutoProxyCreator`：生成 AOP 代理；
- `CommonAnnotationBeanPostProcessor`：处理 `@PostConstruct`、`@Resource`。

`registerBeanPostProcessors` 会把这些后置处理器实例化并注册进容器，顺序是：

1. `PriorityOrdered`；
2. `Ordered`；
3. 没有实现排序接口的；
4. 内部的 `MergedBeanDefinitionPostProcessor` 最后再注册一遍。

为什么要在实例化 Bean 之前做？因为后面的 `getBean` 过程中要用到它们，晚了就赶不上。

## 4. onRefresh：创建 Web 服务器

`onRefresh` 是一个钩子方法，Servlet 容器会在这里创建内嵌 Web 服务器：

```java
@Override
protected void onRefresh() {
    super.onRefresh();
    createWebServer();   // 创建 Tomcat / Jetty / Undertow 对象
}
```

`createWebServer` 内部会：

1. 找到 `ServletWebServerFactory`（Tomcat、Jetty、Undertow 之一）；
2. 调用 `factory.getWebServer(...)` 创建 `WebServer` 对象；
3. 同时创建 `ServletContext`，注册到容器里。

注意：这里只是**创建**服务器对象，端口还没有绑定，请求还进不来。

为什么要在 Bean 实例化之前创建？因为有些 Bean 需要拿到 `ServletContext`，比如 `ServletContextAware` 的实现、Filter、Listener。如果等到所有 Bean 创建完再创建服务器，这些 Bean 就没法注入了。

## 5. finishBeanFactoryInitialization：实例化 Bean

这一步会实例化所有**非懒加载的单例**。核心是 `beanFactory.preInstantiateSingletons()`，它会遍历 BeanDefinition，对每个单例调用 `getBean`。

`getBean` 的链路我们在 [../spring/Spring生命周期.md](../spring/Spring生命周期.md) 里逐行讲过，这里只强调和启动相关的顺序：

- `doCreateBean` 里先实例化，再属性填充，再初始化；
- `@PostConstruct`、`InitializingBean.afterPropertiesSet()`、`init-method` 都在初始化阶段执行；
- AOP 代理在 `postProcessAfterInitialization` 里生成。

**此时 Web 服务器已经创建，但还没有启动。** 所以：

- `@PostConstruct` 里可以拿到 `ServletContext`；
- 但访问本机端口会失败，因为 `webServer.start()` 还没调用。

## 6. finishRefresh：启动 Web 服务器

`finishRefresh` 分两层：

```java
// AbstractApplicationContext
protected void finishRefresh() {
    clearResourceCaches();
    initLifecycleProcessor();
    getLifecycleProcessor().onRefresh();
    publishEvent(new ContextRefreshedEvent(this));   // 发布容器刷新完成事件
}

// ServletWebServerApplicationContext
@Override
protected void finishRefresh() {
    super.finishRefresh();          // 先发布 ContextRefreshedEvent
    WebServer webServer = startWebServer();   // 再启动服务器
    if (webServer != null) {
        publishEvent(new ServletWebServerInitializedEvent(webServer, this));
    }
}
```

`startWebServer()` 才会真正调用 `webServer.start()`：绑定端口、启动 accept 线程、开始接收请求。

所以有一个很重要的细节：**`ContextRefreshedEvent` 发布时，Web 服务器还没有启动。** 如果在这个事件里调用本机接口，一样会失败。真正代表"服务可用"的是后面的 `ApplicationReadyEvent`。

## refresh 结束时的状态

| 时刻 | 容器 | Web 服务器 |
|---|---|---|
| `prepareBeanFactory` 后 | BeanFactory 就绪，有基础设施 Bean | 无 |
| `invokeBeanFactoryPostProcessors` 后 | BeanDefinition 基本齐全 | 无 |
| `registerBeanPostProcessors` 后 | 后置处理器就绪 | 无 |
| `onRefresh` 后 | 还没有 Bean 实例 | 已创建，未绑定端口 |
| `finishBeanFactoryInitialization` 后 | 单例 Bean 创建完成，AOP 代理已生成 | 已创建，未启动 |
| `finishRefresh` 后 | 容器刷新完成 | 已启动，开始接收请求 |

# 第五步：Runner

`refresh()` 结束后，`run` 还会调用 `callRunners`：

```java
private void callRunners(ApplicationContext context, ApplicationArguments args) {
    List<Object> runners = new ArrayList<>();
    runners.addAll(context.getBeansOfType(ApplicationRunner.class).values());
    runners.addAll(context.getBeansOfType(CommandLineRunner.class).values());
    AnnotationAwareOrderComparator.sort(runners);

    for (Object runner : new LinkedHashSet<>(runners)) {
        if (runner instanceof ApplicationRunner) {
            callRunner((ApplicationRunner) runner, args);
        }
        if (runner instanceof CommandLineRunner) {
            callRunner((CommandLineRunner) runner, args);
        }
    }
}
```

`ApplicationRunner` 和 `CommandLineRunner` 都在**容器 refresh 完成、Web 服务器启动之后**执行。适合做：

- 缓存预热；
- 调用本机接口做自检；
- 初始化业务数据；
- 注册健康检查项。

多个 Runner 之间用 `@Order` / `Ordered` 排序。如果 Runner 里抛了异常，会走 `handleRunFailure`，整个应用启动失败。

# 第六步：started / running

最后，`run` 会通知监听器：

```java
listeners.started(context);   // 容器已刷新、Runner 已执行
// ...
listeners.running(context);   // 应用已就绪
```

对应的事件：

- `ApplicationStartedEvent`：`refresh()` 完成、Runner 执行前；
- `ApplicationReadyEvent`：Runner 执行完、应用正式 ready。

如果中间任何一步抛异常，会走 `handleRunFailure`：发布 `ApplicationFailedEvent`、关闭已经创建的 context、把异常抛出去。

# 几个容易混淆的问题

## @PostConstruct、ContextRefreshedEvent、ApplicationReadyEvent 谁先谁后

按时间顺序：

1. **`@PostConstruct`**：在 `finishBeanFactoryInitialization` 里执行，Web 服务器已创建但**未启动**；
2. **`ContextRefreshedEvent`**：在 `finishRefresh` 里发布，`super.finishRefresh()` 先执行，所以此时 Web 服务器**仍未启动**；
3. **`ApplicationStartedEvent`**：`refresh()` 返回后发布，Web 服务器**已启动**，Runner 还没执行；
4. **`ApplicationReadyEvent`**：Runner 执行完后发布，应用**完全就绪**。

所以，如果你要在启动后调用本服务的 HTTP 接口，应该用 `ApplicationRunner` 或监听 `ApplicationReadyEvent`，不要用 `@PostConstruct` 或 `ContextRefreshedEvent`。

## Web 服务器"创建"和"启动"有什么区别

- **创建**：`onRefresh` → `createWebServer`，生成 Tomcat/Jetty/Undertow 对象和 `ServletContext`，但端口没绑定；
- **启动**：`finishRefresh` → `startWebServer` → `webServer.start()`，绑定端口、开始接收请求。

创建在前，是为了让 Bean 能拿到 `ServletContext`；启动在后，是为了保证 Bean 都初始化完再对外服务。

## Environment、ApplicationContext、BeanFactory 的关系

- `Environment`：配置，先于容器存在；
- `ApplicationContext`：容器，持有 `BeanFactory`；
- `BeanFactory`：真正管理 BeanDefinition 和 Bean 实例的地方。

`ApplicationContext` 在 `BeanFactory` 外面加了事件、国际化、资源加载等能力，所以业务代码通常注入 `ApplicationContext`，而不是直接用 `BeanFactory`。

# 小结

我一向不太喜欢写总结，因为该说的正文里都说了。不过考虑到很多读者是冲着面试来的，还是列成清单：

1. **启动分几步？** 构造 `SpringApplication` → 准备 Environment → 创建 Context → prepareContext → refresh → Runner → started/running。
2. **Web 类型怎么推断？** 有 `DispatcherServlet` + `Servlet` → SERVLET；只有 WebFlux → REACTIVE；否则 NONE。
3. **自动装配在启动流程的哪一步？** `refresh()` → `invokeBeanFactoryPostProcessors` → `ConfigurationClassPostProcessor`。
4. **Web 服务器什么时候创建、什么时候启动？** `onRefresh()` 创建，`finishRefresh()` 启动。
5. **`@PostConstruct`、`ContextRefreshedEvent`、`ApplicationReadyEvent` 的顺序？** `@PostConstruct` → `ContextRefreshedEvent` → `ApplicationStartedEvent` → `ApplicationReadyEvent`；前两个执行时 Web 服务器还没启动。
6. **Runner 和 `@PostConstruct` 的区别？** `@PostConstruct` 在 Bean 初始化阶段，服务器还没启动；Runner 在 `refresh()` 之后，服务器已启动。
7. **启动失败怎么处理？** `handleRunFailure` 发布 `ApplicationFailedEvent`、关闭 context、抛出异常。
8. **`ApplicationContextInitializer` 能做什么？** 在 refresh 之前操作 Environment / BeanFactory，不能拿 Bean。
