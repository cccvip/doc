定位、组件地图和版本对应在 [总览.md](总览.md)。这篇按面试题组织，每题给一个能直接说出口的短答。

版本口径以 Spring Cloud 2020.0 之后（对应 Boot 2.4 及以上）为主，涉及 Netlfix 老组件的地方会标出来。

## 一、概念与定位

### Spring Cloud 是什么，和 Spring Boot 什么关系

Spring Cloud 是一组框架的集合，用来解决微服务里的通用问题：注册发现、配置管理、网关、容错、链路追踪、分布式事务。它构建在 Spring Boot 之上——每个组件本身就是一个 Boot 应用或 starter。所以关系是：Boot 负责把单个服务跑起来，Cloud 负责让多个服务协同起来。

### Spring Cloud 提供了哪些能力

按职责分：注册中心（Nacos、Eureka）、配置中心（Nacos Config、Config）、服务调用（OpenFeign）、负载均衡（LoadBalancer）、网关（Gateway）、容错限流（Sentinel、Resilience4j）、链路追踪（Micrometer Tracing）、分布式事务（Seata）。面试时能按这七块报出来就够了。

### 版本怎么和 Spring Boot 对应

Spring Cloud 用 train 名而不是普通版本号，每个 train 只兼容特定范围的 Boot。记一条线：Boot 2.2/2.3 对应 Hoxton，2.4/2.5 对应 2020.0，2.6/2.7 对应 2021.0，Boot 3.x 对应 2022.0 及以后。选版本时这两个必须成对，装错直接起不来。

### 2020.0 之后有哪些大变化

两件。Ribbon、Hystrix、Zuul 被移除，换成 LoadBalancer、Resilience4j 或 Sentinel、Gateway；配置默认不再走 bootstrap，改用 `spring.config.import`。看到老文章讲 Ribbon/Hystrix，要自己折算。

### Spring Cloud 和 Spring Cloud Alibaba 有什么区别

Spring Cloud 是基础规范加一堆官方实现；Spring Cloud Alibaba 是阿里出的、符合这套规范的另一组实现，重点是 Nacos、Sentinel、Seata，还补了 RocketMQ、Dubbo 的集成。国内项目基本是 Alibaba 系。

### Spring Cloud 和 Dubbo 的区别

Spring Cloud 是整套微服务方案的集合，默认走 HTTP/REST，生态全但单次调用开销略大；Dubbo 更偏高性能 RPC 框架，默认用自研 Dubbo 协议配合注册中心做治理。两者可以一起用：内部调用走 Dubbo，外围网关、配置、链路用 Spring Cloud。

## 二、注册中心

### 服务注册与发现的流程

提供者启动时把自己的 IP、端口、元数据注册到注册中心，并定期发心跳；消费方从注册中心拉一份实例清单，缓存在本地，调用时从清单里挑一个。清单会定期更新，感知实例上下线。

### Nacos 和 Eureka 的区别

Eureka 只做注册中心，是 AP 模型，任何时刻都保证可用、容忍短暂不一致。Nacos 既是注册中心也是配置中心，而且能按实例类型切模型：临时实例走 AP，持久实例走 CP（基于 Raft）。功能上 Nacos 更全，所以现在默认选它。

### Eureka 的自我保护机制是什么

Eureka 服务端会统计心跳续约的比例，如果短时间内掉得太多（默认阈值 85%），它就不再把实例剔除，宁可保留可能已经挂掉的实例。目的是防止网络抖动导致大批服务被误判下线。代价是故障实例会被多保留一段时间。

### 服务宕机，消费方多久能感知

分三步看：提供者停止心跳、注册中心把它剔除、消费方刷新本地清单。Eureka 这套走下来通常要一到两分钟（心跳默认 30 秒、剔除定时 60 秒、客户端拉取 30 秒）。Nacos 因为有推送，感知快得多。这段时间里消费方可能调到一个死实例，所以调用侧还要有重试和熔断兜底。

## 三、配置中心

### 配置中心解决什么问题，Nacos Config 和 Config 有什么区别

把散在各服务里的配置集中管理，支持多环境、多命名空间、动态刷新、灰度。Spring Cloud Config 依赖 Git 或后端存储，变更靠客户端定时拉取或手动触发刷新；Nacos Config 自带管理界面，用长轮询做变更推送，刷新更及时。国内一般用 Nacos。

### 配置动态刷新怎么实现

配置中心的客户端在启动时拉取配置，之后保持长轮询或定时拉取。服务端有变更时通知客户端，客户端拿到新值后刷新对应的配置对象。用 `@RefreshScope` 标注的 Bean 会在刷新时被重建，从而拿到新值。注意 `@RefreshScope` 重建的是 Bean 本身，如果配置是用 `@Value` 注入到普通单例里的，不标这个注解不会更新。

### 配置加载时机，bootstrap 和 application 有什么区别

早期用 `bootstrap.yml`，它比 `application.yml` 先加载，用来放配置中心的连接信息——因为要先连上配置中心、才能拉到业务配置。从 Boot 2.4 起 bootstrap 默认关闭，改在 `application.yml` 里用 `spring.config.import` 声明配置来源。面试问到这里，能说清"为什么要有个更早的阶段"比记文件名重要。

## 四、服务调用与负载均衡

### OpenFeign 的原理

你写一个接口、加上 `@FeignClient`，Feign 在启动时用动态代理生成实现。调用方法时，代理把方法名、参数按约定拼成 HTTP 请求，交给负载均衡器选实例，再发出去，最后把响应解码成返回值。整个过程对使用者就是"调本地方法"。

### OpenFeign 和 RestTemplate 的区别

RestTemplate 要手写 URL 和参数、自己处理拼接，是命令式的；OpenFeign 声明式，接口即契约，代码更干净，还天然接入了负载均衡。现在基本都用 Feign。

### 负载均衡算法有哪些，客户端和服务端负载均衡的区别

常见算法：轮询、随机、加权、最少连接、一致性哈希。客户端负载均衡是消费方自己从实例清单里挑（LoadBalancer、老的 Ribbon），服务端负载均衡是先到中间的负载器、由它转发（Nginx、LVS）。前者的好处是不用多一跳、能感知服务清单，后者更集中、更好统一管控。

### Ribbon 和 Spring Cloud LoadBalancer 的区别

Ribbon 是 Netflix 的、已经废弃；LoadBalancer 是官方替代品，默认策略是轮询。老项目还在用 Ribbon，新项目一律 LoadBalancer。

## 五、网关

### 网关的作用和三大概念

网关是流量的统一入口，负责路由、鉴权、限流、灰度、日志。三个核心概念：路由（Route，由 id、目标 uri、断言、过滤器组成）、断言（Predicate，匹配请求条件）、过滤器（Filter，在转发前后做处理）。网关部分可以先看现有的 [SCG 调优分析](../../practice/SCG.md)。

### Gateway 和 Zuul 的区别

Zuul 1 基于 Servlet，是阻塞模型；Spring Cloud Gateway 基于 WebFlux 和 Reactor Netty，是异步非阻塞的，并发能力更好。Zuul 也已经随 Netflix 组件一起退场，新项目用 Gateway。

### Gateway 怎么做限流和鉴权

限流用自带的 `RequestRateLimiter` 过滤器，配合一个 KeyResolver 决定按什么维度限流（IP、用户、接口），底层通常用 Redis 计数。鉴权一般写一个全局过滤器，在转发前校验 token，不通过就直接返回。

## 六、容错

### 熔断、降级、限流的区别

三者目标不同。限流是控制入口的请求速率，超了就拒绝，保护自己不被压垮。熔断是当依赖的失败率或慢调用比例超过阈值，直接切断对它的调用，不再白白等待。降级是切断或失败后返回一个兜底结果，比如默认值、缓存值、友好提示。一般是限流挡住入口、熔断切断坏依赖、降级给出兜底。

### Sentinel 和 Hystrix 的区别

Hystrix 靠线程池或信号量做隔离，粒度重、配置不够灵活，已经停更；Sentinel 用滑动窗口统计指标，规则可以动态下发，支持流控、熔断、热点参数、系统自适应保护，默认用信号量模型、开销更小，还带一个可视化控制台。国内基本用 Sentinel。

### 熔断器的状态机

三个状态：CLOSED（正常放行，统计失败率）、OPEN（失败率超阈值，直接拒绝）、HALF_OPEN（OPEN 持续一段时间后放少量请求试探）。试探成功回到 CLOSED，失败重新回 OPEN。面试常追问"半开状态的意义"——避免在依赖恢复前就把它完全放回来。

### 服务雪崩是怎么发生、怎么防

下游某个服务变慢，上游的调用线程被长时间占用，线程池满了之后上游也变慢，一级级往上传染，最后整条链路卡死。防护手段：给调用设置合理超时、用熔断切断坏依赖、做资源隔离（不同依赖用不同线程池或信号量）、入口限流、不可用时降级返回兜底。

## 七、链路追踪

### 链路追踪的原理

一次请求进来分配一个全局唯一的 TraceId，每经过一个服务或一段调用生成一个 SpanId 记录耗时和层级关系，这些标识通过请求头在服务之间传递。所有数据汇总到后端（Zipkin、SkyWalking）就能拼出完整调用链，用来定位慢在哪一段。

### Sleuth 和 Micrometer Tracing 是什么关系，标识怎么传递

Sleuth 是老的追踪方案，从 Spring Cloud 2022.0 起被 Micrometer Tracing 取代。传递方式是：调用方把 TraceId、SpanId 放进请求头（HTTP 用约定的头，消息队列用消息属性），被调方读出来继续往下传。为了控制开销一般会采样，不是每条请求都完整记录。

## 八、分布式事务

### Seata 的角色和模式

三个角色：TC（事务协调者，独立部署，管全局事务的提交回滚）、TM（事务管理器，业务里发起全局事务的一方）、RM（资源管理器，管每个分支事务）。四种模式：AT（无侵入，最常用）、TCC（手写 try/confirm/cancel）、SAGA（长事务、补偿）、XA（依赖数据库 XA）。日常聊 AT 最多。

### AT 模式的原理

执行业务 SQL 时，Seata 拦截并记录数据的前后镜像（undo log）。一阶段各分支先各自提交本地事务、释放本地锁；二阶段全局提交就异步清理 undo log，全局回滚就拿 undo log 反向补偿。为了写隔离，Seata 在更新前会申请全局锁，避免两个全局事务交叉改同一行数据。

## 九、综合

### 微服务里常见的坑

调用重试可能被放大——上游重试会叠加下游重试，流量成倍增长，所以重试要设上限、配合熔断。还有最终一致性问题、链路变长带来的排障困难、配置和版本管理复杂。面试里能主动提到"重试放大"和"超时要层层配置"，比只背组件更有说服力。
