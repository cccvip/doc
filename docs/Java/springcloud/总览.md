Spring Cloud 不是一个框架，是一组框架的集合。它把分布式系统里反复出现的那几个问题——服务怎么互相找到、配置怎么统一管、调用失败了怎么不雪崩、外部流量怎么收口——各给了一套基于 Spring Boot 的实现。

所以面试问"Spring Cloud 是什么"，答"一套微服务解决方案的工具箱"比答"一个 RPC 框架"要靠得住。

## 它在解决什么问题

单体拆成多个服务之后，会冒出一串新麻烦。

服务地址会变，A 要调 B，不能把 B 的 IP 写死；配置散在几十个服务里，改一个参数不想挨个重启；某个下游慢了或挂了，调用方不能跟着一起拖死；外部的请求需要一个统一入口，做鉴权、限流、路由。这些问题在微服务里几乎人人都会撞上，Spring Cloud 把每一个都做成了组件。

## 组件地图

按职责分，常用的这些：

- 服务注册与发现：Nacos、Eureka、Consul、Zookeeper
- 配置中心：Nacos Config、Spring Cloud Config
- 服务调用：OpenFeign（声明式），也可以 RestTemplate 或 WebClient 配负载均衡
- 负载均衡：Spring Cloud LoadBalancer
- 网关：Spring Cloud Gateway
- 容错限流：Sentinel、Resilience4j
- 链路追踪：Micrometer Tracing + Zipkin / SkyWalking
- 分布式事务：Seata
- 消息驱动：Spring Cloud Stream
- 安全：Spring Cloud Security / OAuth2

## 两套主流形态

早期是 Netflix 系：Eureka 做注册中心，Ribbon 做负载均衡，Hystrix 做熔断，Zuul 做网关。这套现在基本退场了。

国内主流是 Alibaba 系：Nacos 做注册中心和配置中心，Sentinel 做限流熔断，Seata 做分布式事务，配 OpenFeign 和 Gateway。面试被问得最多的就是这一套。

## 版本：release train 和 Boot 强绑定

Spring Cloud 不用普通版本号，用 train 名（Hoxton、2020.0、2021.0……），每个 train 只兼容特定范围的 Spring Boot。粗记一条线：

- Boot 2.2 / 2.3 → Hoxton
- Boot 2.4 / 2.5 → 2020.0
- Boot 2.6 / 2.7 → 2021.0
- Boot 3.x → 2022.0 及以后

有两个变化值得单独记牢。

一是 2020.0 起，Netflix 的 Ribbon、Hystrix、Zuul 全部被移除，对应换成 Spring Cloud LoadBalancer、Resilience4j 或 Sentinel、Spring Cloud Gateway。所以看到老文章讲 Ribbon 和 Hystrix，要自己折算成新组件。

二是从 Boot 2.4 起，配置默认不再走 bootstrap，改成 `spring.config.import`。以前讲"配置放 bootstrap.yml"的做法在新版本里要调整。

## 核心机制，每个一句话

注册发现：服务启动时把自己的地址注册到注册中心，消费方从注册中心拉一份实例清单并在本地缓存，之后靠心跳维持在线状态。

配置中心：客户端启动时拉取配置，再通过长轮询（Nacos）或定时拉取（Config）感知变更，服务端有改动就通知客户端刷新。

负载均衡：消费方拿到实例清单后自己挑一个，这叫客户端负载均衡，和 Nginx 那种"请求先到中间、由中间转发"的服务端负载均衡不是一回事。

网关：请求先进网关，按路由规则匹配，经过过滤链做鉴权、限流、改写，再转发到具体服务。

容错：调用失败或超时触发降级；连续失败达到阈值触发熔断，过一段时间进入半开状态试探，恢复了就闭合。

## 和 Dubbo 的区别

先记结论。Spring Cloud 是一整套微服务方案的集合，默认走 HTTP/REST，生态齐全；Dubbo 更像一个高性能 RPC 框架，默认用自研的 Dubbo 协议（也支持 gRPC、HTTP），配合注册中心做服务治理。

两者不冲突。Spring Cloud Alibaba 里常见的做法是：服务之间的内部调用用 Dubbo 走 RPC，外围的网关、配置、链路用 Spring Cloud 兜住。
