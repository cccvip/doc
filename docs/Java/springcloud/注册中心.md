一次很常规的发布，商品服务滚动重启。发布完，监控上出现一个说不通的现象：大部分流量已经切到新实例，但仍有一小撮请求打在已经停掉的旧 IP 上，报 `connection refused`，前后持续了大约四十秒才干净。

旧实例确实下线了，注册中心控制台里也查不到它。那这四十秒的请求是从哪来的？

## 第一层：注册中心已经干净了，调用方为什么还在打旧地址

第一反应通常是"注册中心没把旧实例摘掉"。但去看控制台，旧实例早就没了；剩下实例的心跳都正常，健康状态也是 UP。注册中心这边没毛病。

第二反应是"调用方缓存没清"。这个方向对了一半，但还不够。

真正的原因是：**调用方根本不会每次调用都去问注册中心**。它手里有一份从注册中心同步过来的实例清单，存在本地，调用时直接从这份清单里挑。清单是异步更新的——旧实例从注册中心消失，不等于它立刻从每个调用方的内存里消失。

而且即便清单更新了，调用方到旧实例之间可能还留着已经建立的连接，负载均衡器里也可能还缓存着上一份列表。所以"注册中心干净了"和"没有请求再打过去"之间，隔着好几件事。

## 第二层：把"下线"拆成四段

这四十秒不是一个原因造成的，而是四段延迟叠出来的。

| 阶段 | 谁在做 | 大致耗时 | 说明 |
|---|---|---|---|
| 进程退出 | 应用 | 立即 | 收到 SIGTERM，进程结束，停止发心跳 |
| 注册中心感知 | Nacos 服务端 | 秒级到三十秒 | 主动注销是即时的；否则等心跳超时或连接断开 |
| 变更推送 | 服务端 → 订阅方 | 毫秒级到秒级 | 2.x 走 gRPC 长连接推 |
| 调用方生效 | 消费方 | 取决于缓存和连接 | 更新清单、清理连接池、在途请求跑完 |

多数人只盯着第二段，实际上第一段和第四段同样会拖时间。下面逐段说。

## 注册时到底发生了什么

先把数据模型摆清楚，不然"服务"和"实例"容易混。

Nacos 的隔离层级从大到小是：命名空间（namespace）、分组（group）、服务（service）、集群（cluster）、实例（instance）。一个服务是逻辑概念，一个实例是某台机器上的具体进程。同一个服务可以在多个集群里各有若干实例，集群通常对应机房或可用区。

服务启动时，客户端把 IP、端口、集群、权重、元数据，以及一个很关键的标记——是不是**临时实例**——报给服务端。这个标记决定了后面两件事：实例靠什么维持存活，以及数据走哪套一致性协议。

默认是临时实例。Spring Cloud Alibaba 里对应 `spring.cloud.nacos.discovery.ephemeral=true`，绝大多数业务用的都是它。

服务端收到注册后，把实例写进这个服务对应的数据结构，然后异步同步给集群里的其他节点。注意"异步"两个字，它意味着注册完成后，不同节点上看到的实例列表可能短暂不一致。

## 心跳和健康检查：5/15/30 是怎么来的

临时实例靠客户端心跳维持。默认节奏是三档：

- 客户端每 **5 秒**发一次心跳；
- 服务端超过 **15 秒**没收到，把实例标记为不健康；
- 超过 **30 秒**还没收到，才真正摘除。

这三个数不是随便定的，比例是 1 : 3 : 6。5 秒是探测精度，15 秒给网络抖动留一次容错，30 秒再给一次，避免偶发丢包就把实例摘掉。三个值都能配，但改小会增加服务端压力，改大会拉长故障感知时间，要按业务权衡。

服务端不是收到心跳就完事，它还有一个定时扫描的任务，按上面的阈值把实例从"健康"挪到"不健康"、再挪到"摘除"。所以从进程停止到注册中心动手，本身就有几十秒的空间。

持久实例是另一套逻辑：它不靠客户端心跳，而是由服务端主动探测（TCP、HTTP 或 MySQL 检查），探测失败才标记不健康。因为不依赖客户端，它适合那些不由 Nacos 客户端管理、或者需要强一致的场景。

## 2.x 改了什么：从短连接到长连接

1.x 的心跳走 HTTP 短连接，每次都要建连、发请求、断开，服务端还要处理大量定时拉取，开销不小。

2.x 换成了 gRPC 长连接。客户端和服务端保持一条双向流，心跳、注册、订阅、推送都复用这条连接。带来的变化有三个：

一是开销小了，不用反复建连；二是服务端能直接感知连接断开，实例失联的发现比等心跳超时更快；三是推送变成真正的服务端主动推，不再依赖 1.x 那套 UDP 通知加客户端长轮询兜底。

要说明一点：2.x 并没有把 5/15/30 这套健康检查阈值废掉。连接断开是另一条更快的路径，阈值仍然负责处理"连接还在、但客户端已经不干活"这类假死。

## 变更是怎么传到调用方的

调用方启动时订阅自己关心的服务。服务端记下这个订阅关系，之后这个服务的实例有任何增减，就把变更推给它。

客户端收到推送后更新本地缓存——也就是前面说的那份实例清单。除了推送，客户端通常还有一个兜底的定时全量更新，防止推送丢失导致长期不一致。

所以调用方要"看到"一次变更，至少经过：服务端变更、推送到达、客户端更新缓存。这三步都不慢，但都不是零。

这也解释了本地缓存为什么不能省。有人会问：既然缓存会带来延迟，为什么不每次调用都实时问注册中心？因为那样注册中心就成了整个系统的单点：它一抖动，所有调用跟着卡；它一挂，所有服务立刻不能互相调用。缓存的意义就是让注册中心短暂不可用时，调用方靠旧清单还能继续工作。

代价就是开头那四十秒。缓存越抗故障，就越不可能实时，这是取舍，不是 bug。

## AP 还是 CP：Nacos 是按数据分的

这是注册中心话题里最容易被追问的一点，也最容易被答成一句空话。

先说结论：Nacos 不是整体二选一，而是按数据类型走两套协议。

**临时实例走 AP，底层是 Distro。** Distro 是阿里自研的一套分布式协议，思路接近 Gossip，但有明确的分片责任：每个节点负责一部分服务的写入，写的时候只写自己负责的那片，读也优先读本地，然后异步复制给其他节点。节点之间还会定时全量对账，新节点加入时拉一份快照。

这套设计在正常情况下的表现是：写入快、读取快、某个节点挂了不影响整体。代价是不同节点之间是最终一致，网络分区时可能看到过时数据。

**持久实例以及需要强一致的数据走 CP，底层是 Raft。** Raft 大家都熟：选主、日志复制、多数派确认。写入要等多数节点落盘才算成功，所以一致性强，但延迟和可用性都有代价。

所以准确的说法是："服务发现用临时实例，就是 AP；需要强一致的场景用持久实例，就是 CP。"面试里能说到"按实例类型分"，而不是"Nacos 是 AP"或"Nacos 是 CP"，就已经高一个层次了。

顺着这个还能回答另一个常见问题：**注册中心全挂了，服务还能不能调？** 能调，只要调用方有本地缓存、到提供方的网络还通。但系统是"冻结"的——新实例发现不了，下线的也感知不到，只能等注册中心恢复。这也正说明了为什么客户端要缓存、为什么注册中心本身要做集群。

## 那四十秒里，还有哪些容易忽略的坑

**没有主动注销，直接 kill。** 滚动发布时如果进程收到 SIGTERM 就直接退出，没调注销接口，注册中心只能等心跳超时或连接断开。这一段的延迟就是十几到三十秒。主动注销是同步生效的，能把这几十秒直接省掉。

**清单更新了，连接池没更新。** HTTP 客户端或 RPC 框架一般会维持长连接池。旧实例虽然从清单里消失了，池子里指向它的连接可能还在，下一次复用就会失败。

**重试把问题放大了。** 一次失败触发重试，重试又可能被下一层再重试，流量成倍打向那台已经死掉的机器，四十秒被拉得更长，还可能拖累其他实例。

**多网卡注册错 IP。** 机器有多张网卡时，客户端默认可能选了 docker0 或虚拟网卡的地址，注册上去的 IP 从外面根本不通。这类问题表现为"实例是健康的，但就是连不上"，排查时容易绕远。

## 发布时到底该怎么做

回到开头那次发布。问题不在于注册中心慢，而在于**停进程和摘流量几乎同时发生**。

正确顺序是反过来的：先让流量停掉，等调用方感知、在途请求处理完，再停进程。

- 发布前主动注销，或者把健康状态置为 DOWN；
- 等一段时间，长到覆盖服务端推送和调用方缓存刷新；
- 再走优雅停机，等在途请求跑完；
- 最后才真正退出进程。

在 Kubernetes 里，这对应 `preStop` 钩子加一段等待，并给 `terminationGracePeriodSeconds` 留足时间。Boot 自带的 `server.shutdown=graceful` 只解决"处理完在途请求"，不解决"别人还在往你发新请求"，两者要配合。

调用方这边也不能全指望注册中心。合理设置超时、失败重试换实例、连续失败熔断，是最后一道兜底。

## 面试怎么答

被问到注册中心，建议按这个顺序：

先讲数据模型和注册流程——服务与实例、临时与持久、默认走临时实例。再讲健康检查的 5/15/30 和它背后的 1:3:6 取舍。然后讲变更怎么传到调用方：订阅、推送、本地缓存，以及缓存带来的延迟。最后用一次发布事故收尾，说明为什么"摘流量"和"停进程"要分开。

追问 Nacos 的 AP/CP，就答"按数据类型分"：临时实例 AP（Distro，分片责任、本地读、异步复制），持久实例 CP（Raft，多数派）。追问 2.x 的变化，就答 gRPC 长连接替代 HTTP 短连接，心跳、订阅、推送复用一条连接，断开能被更快感知。
